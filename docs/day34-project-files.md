# День 34: ассистент для работы с файлами проекта

Источник требований — `../ai-advent-challenge-9/week7/day34/README.md`, контекст — вся неделя 7.
Решение — ff.ai: MCP даёт поиск и чтение, локальный корпус — контекст,
конвейер связывает исследование, разработку, независимое ревью и подтверждённую запись.

## Субагенты

Главный агент собирает актуальные файлы и источники, строит план и управляет записью.
Разработчик получает отдельный запрос с целью, пунктом плана и контекстом проекта;
возвращает unified diff. Ревьюер получает собственную ролевую инструкцию, цель,
актуальные источники и только извлечённый diff. История диалога и рассуждения
разработчика в его запрос не входят. Это отдельные модельные вызовы одной модели
сессии, а не процессы и не независимые писатели в проект.

До ревью код проверяет пути, применимость патча и правила домена. При замечаниях
разработчик получает одну попытку исправления в текущей операции. Исправленная
версия проходит те же проверки и новое независимое ревью. Недоступный ревьюер,
некорректный или обрезанный ответ и повторные замечания блокируют запись;
прогон встаёт на паузу, причина остаётся в задаче. Автоматический повтор после
этого не запускается. Пользователь может явно продолжить или остановить задачу.

Положительное ревью не подтверждает запись: TUI/web отдельно показывают diff
и спрашивают пользователя. Применение, устойчивые снимки, восстановление и undo
используют существующий журнал `ProjectChanges`. Полный прогон сохраняет также
обычную проверку артефакта после записи. Ревью не заменяет сборку и тесты.
Роли, токены, время, стоимость и замечания видны в результатах этапа и `/task`,
сохраняются в состоянии задачи и её Markdown-отчёте. Расход входит в `/usage`.

## Три цели для демонстрации

1. «Найди, как реализовано создание папки и где используется соответствующая
   операция. Ничего не меняй. Прочитай реализацию, объявление и вызывающий код».
   Показать автоматический поиск/чтение и источники минимум из трёх файлов.
2. «Создай краткий документ о создании папки: путь от контроллера до сетевой
   операции, результат и обработка ошибок. Сам найди исходники. Создай один
   Markdown-файл в docs. Изменения ограничь документацией».
   Показать разработчика, ревьюера, diff, подтверждение и созданный файл.
3. «Защити создание папки от повторного запуска, пока операция выполняется.
   После успеха или ошибки новый запуск должен работать. Добавь проверку
   поведения и обнови созданный документ».
   Выполнить три подзадачи: контроллер → автономный тест → обновление документа.
   У каждой отдельные разработчик, ревью и подтверждение diff.
   План проверяется до записи; одна корректировка допустима, повторный уход от цели останавливает демо.
   Проверить два последовательных вызова и повторный запуск после успеха/ошибки.

Цели разработки передаются штатными `/task add <цель>` и `/task run`,
сохраняя формулировку пользователя. Исследование идёт обычным вопросом.
Пути входных файлов не задаются пользователем. Для WebDavClient контрольная
область — операция создания папки, её объявление и вызывающий контроллер.
Упоминание класса в forward declaration не следует выдавать за вызов операции.

## Повторение

Из корня ff.ai:

```bash
.venv/bin/python scripts/day34_demo.py \
  --source /path/to/WebDavClient \
  --output videos/day34-dry-run.json
```

Сценарий использует живую модель и настоящий локальный MCP. Перед записью
он создаёт копию отслеживаемых обычных файлов WebDavClient, исключает `.env`
и редактирует распознанные секреты. Переменные FFAI перенаправляют состояние,
историю, память, профиль, задачи, журнал, индекс и выгрузки в отдельный каталог.
Исходный WebDavClient и пользовательское состояние не изменяются.

Каждый запуск требует нового файла результата. Временная копия сохраняется
для проверки; её путь печатается локально, а в сохраняемых JSON заменяется
шаблоном. Артефакты содержат результаты, diff, журнал, источники и расход;
неуспех обозначается статусом failed и ненулевым кодом выхода.

Без флагов diff подтверждается интерактивно. `--approve-demo` заранее разрешает
только показанные патчи в пределах цели: Markdown в docs, целевой контроллер
и проверки в tests. Это разрешение действует только внутри временной копии.
Остальные пути отклоняются. Для записи настоящего TUI добавьте
`--visible --approve-demo`, используя пустой `--workspace` и рекордер
`.agents/skills/solve-challenge-task/scripts/record_screen.sh`.

Формулировка «не меняй исходники» включает общий запрет записи и потому не
подходит цели создания документа: границу записи задавайте положительно,
например «изменения ограничь документацией». Это консервативное правило
существующего маршрутизатора намерений.

## Проверки и материалы

Заглушки модели проверяют изоляцию, последовательность, отказ и журнал;
они не доказывают качество живого ответа. Полный локальный набор:

```bash
.venv/bin/python -m pytest -m 'not network' -q
```

Сухой прогон предшествует записи. Видео проверяется по длительности 30–600
секунд и ключевым кадрам. Недоступные сборка, тесты или запись указываются
по фактической причине; их нельзя объявлять успешными.

Материалы сдачи — `videos/day34-demo.mp4`, `videos/day34-README-draft.md`
и `videos/day34-release-notes.md`, когда эти файлы действительно подготовлены.
Следующий предлагаемый номер — v0.34 после v0.33. Ссылка на код строится
по фактическому тегу; URL видео добавляется только после реальной загрузки.

Демонстрация выбирает `glm-5.3-flash` штатным механизмом выбора модели;
`--model` позволяет выбрать другое доступное имя. Для другой модели уровень
рассуждений по умолчанию не отправляется; `--reasoning-effort` задаёт его явно. Для исследования используются
MCP-источники без локального RAG. Для документирования RAG включается, а кодовые
подзадачи получают актуальные локальные файлы при выключенном повторном MCP-флоу.
Бюджет — до шести файлов, до 12 000 символов на файл и 80 000 символов суммарно.
Потолок плана — три пункта, маленькая цель документа допускает один пункт.
Предел патча — 2000 слов, планирования/маршрутизации и ревью — 1500 слов,
таймаут запроса — 90 секунд. Для GLM демо задаёт `FFAI_REASONING_EFFORT=low`.
В обычном запуске настройка пуста: параметр API не отправляется.
Для поддерживающих провайдеров доступны `low`, `high`, `max`; неверное значение
отклоняется до сетевого запроса. Все настройки изолированы процессом демо.

Проверка результата компилирует реальные тела методов контроллера с подменами
Qt и сетевой операции. Исходный код должен провалить проверку двойного запуска;
изменённый — пройти её и повторный запуск после успеха и ошибки. Эта проверка
не доказывает доставку Qt-сигналов, работу сервера или сборку всего приложения.
Сценарий также проверяет создание документа со ссылками на три прочитанных
исходника и его обновление. Созданный автономный Python-тест запускается отдельно:
в копии с исходным контроллером он должен завершиться ошибкой, после правки — успешно.
Каждый запуск ограничен 45 секундами; переменные ключей, токенов и паролей исключены
из окружения, дочерние процессы завершаются при таймауте или прерывании.
Постоянно успешный или постоянно падающий тест не принимается.

Промежуточная попытка исправления сохраняется как `review_pending`. Если процесс
прерван, следующий запуск ставит задачу на паузу. Продолжение не пропускает
незавершённое ревью: нужно остановить эту задачу и повторить цель. Пустой или
обрезанный ответ разработчика также ставит прогон на паузу. `content: null`
провайдера трактуется как пустой ответ с сохранением метрик.

MCP-конфигурация копии демо разрешает чтение и read-only Git, но запрещает
`repo_run`: полная сборка явно показывается как недоступная по политике демо.
Это предотвращает запуск системного qmake macOS вместо целевого SDK и появление
побочных сборочных файлов в корне копии. SDK, цели и исходный проект не меняются.
Доступная проверка логики контроллера выполняется отдельным C++-прогоном.

У модельного ответа с заголовками `diff --git` пересчитываются числовые длины
hunk. Пути, позиции и строки не меняются. Повреждённый контекст не восстанавливается:
строгий разбор, правила домена и `git apply --check` остаются до ревью и записи.

Файлы, уже названные целью или планом, получают приоритет в контексте исполнения
и читаются за пределами прежних MCP-диапазонов в пределах бюджета. Для обычной
проверки артефакта демо допускает два цикла; отказ независимого ревью продолжает
останавливать прогон до решения пользователя.

Проверка и применение используют `git apply --unidiff-zero`, чтобы корректные
минимальные блоки без хвостового контекста не считались концом файла. Чужой
контекст отклоняется; разбор, границы путей, снимки, ревью и подтверждение сохраняются.
Источники документа проверяются по фактическим чтениям исследования и его задачи.

Демонстрационный флоу ограничен тремя раундами и восемью вызовами инструментов на сбор контекста.

Контрольный прогон упрощённого сценария на `glm-5.3-flash` остановился до кодовой
цели: разработчик подготовил допустимый документ, но ответ независимого ревьюера
не прошёл строгую проверку JSON. Патч не применён, исходный WebDavClient сохранён.
Успешное живое демо и видео пока не получены. Повторы и смена модели в этом
контрольном прогоне не выполнялись.

JSON-контракт ревьюера исправлен отдельным шагом. Для `task_review` на
`glm-5.3-flash` штатного OpenCode Zen отправляется `response_format=json_schema`
с единственным полем `issues`: до десяти непустых строк по 2000 символов.
Поддержка проверена короткими запросами, включая противоречие между пользовательским
JSON и требуемым схемой полем: endpoint вернул поле схемы. Это наблюдение для данной
пары модели и endpoint. Остальные модели и нестандартный `OPENCODE_API_URL`
сохраняют прежний запрос; fallback после ошибки API отсутствует. Код независимо
от API отклоняет неправильный JSON, лишние поля и обрезание.

При отказе журнал задачи сохраняет причину, `finish_reason`, длину и до 2000
символов очищенного и JSON-экранированного ответа. Секреты удаляются до усечения.
Диагностика не отправляется разработчику и не входит в историю диалога.
[Документация Z.AI](https://docs.z.ai/guides/capabilities/struct-output) описывает
JSON mode и проверку схемы приложением; поддержка JSON Schema именно в Zen
подтверждена указанным экспериментом, а не предполагается из этой документации.

Первый контрольный запуск после изменения остановился раньше ревью:
маршрутизатор запросил уточнение исследования. Позже отдельный запрос выявил
запрет DNS в песочнице; маршрутизатор также преобразует ошибки API в уточнение,
поэтому этот результат не доказывает сбой классификации моделью.
Артефакт — `videos/day34-json-schema.json`, исходный WebDavClient сохранён.

Отдельное живое ревью ранее отклонённого diff документа вне песочницы прошло:
`issues=[]`, `finish_reason=stop`, 7828 токенов, около четырёх секунд.
Использованы текущая схема, прежний diff и пять исходных файлов. Патч не применялся.
Артефакт `videos/day34-json-review-check.json` подтверждает контракт ревью,
но не подменяет полный сценарий изменения проекта.

Полный контрольный прогон вне песочницы (`videos/day34-json-schema-live.json`)
выполнил пять ревью без ошибки JSON. Документ прошёл замечание, исправление и
одобрение; защита контроллера также прошла ревью и применена в копии.
Обе версии автономного теста отклонены по содержанию: первая вручную повторяла
логику на Python, вторая пыталась транслировать C++ в Python с ошибками обработки
`return` и получения исходника через `inspect.getsource` для `exec`-функций.
Тест не применён, прогон остановлен на втором кодовом шаге. Третий шаг и финальные
проверки поведения не выполнялись; видео не записано. Оригинал не изменён.
Это оставшаяся проблема качества генерации теста, а не нарушение JSON-контракта.
Локальный набор после исправления контракта: 1622 passed, 11 сетевых deselected.
После остановки отдельная C++-проба реальных методов изменённого контроллера
прошла двойной вызов и новый запуск после успеха и ошибки
(`videos/day34-json-controller-check.json`). Она не заменяет отклонённый
сгенерированный тест или полный сценарий. Независимая проверка также подтвердила
ошибки транслятора и `inspect.getsource`, указанные модельным ревьюером.
