# День 32: автоматическое AI-ревью кода

Источник: `../ai-advent-challenge-9/week7/day32/README.md`.
Контекст: `../ai-advent-challenge-9/week7/README.md`.
Решение: ff.ai; проект для подключения и демонстрации — личный WebDavClient.

## Критерии дня

Ассистент должен:

- получать diff и изменённые файлы;
- использовать RAG (документация + код);
- выдавать текст ревью.

Минимальный результат:

- пайплайн (например GitHub Action) запускается на PR;
- ассистент получает diff;
- возвращает потенциальные баги, архитектурные проблемы, рекомендации.

Формат сдачи — видео + код.

Неделя 7 объединяет инструменты, память/RAG и автоматизацию в полезный конвейер.
Здесь используется последовательная цепочка «изменения → RAG → ревью → отчёт»:
этапы имеют статусы и время, один запрос модели получает подготовленный контекст.
Субагенты не являются обязательным критерием дня 32 и в этом конвейере не используются.

## Локальный запуск

```bash
cd /path/to/ff.ai
.venv/bin/python ff-ai-review.py \
  --repo /path/to/aurora-project --domain aurora-qt5 \
  --base main --head HEAD --output /path/to/review-results
```

Каталог результатов должен быть пустым и находиться вне целевого проекта.
Ключ берётся из `OPENCODE_API_KEY`, как в интерактивном ff.ai; модель выбирается
`--model`. Данные из рабочего дерева не используются: содержимое читается из
head, diff строится от merge-base с base. Изменения и git-index проекта сохраняются.

Результаты:

- `review.md`: потенциальные баги, архитектурные проблемы, рекомендации и фактически доставленные источники;
- `report.json`: разрешённые SHA, список изменений, статусы и время этапов, RAG-фрагменты, ограничения, расход модели, структурированные findings и решение gate.

RAG использует правила корпуса домена и существующий baseline-поиск по токенам.
Документы Markdown и исходники ищутся раздельно: до четырёх фрагментов каждого типа.
Для документов выбирается не более одного фрагмента одного файла, чтобы длинный README
не вытеснил соглашения разработки. Diff доставляется после скрытия учётных данных
в полных base/head-текстах; метаданные git сохраняют изменения режимов файлов.
Индексы и снимок создаются во временном каталоге рядом с результатами и удаляются
по завершении. История, память и другие пользовательские файлы не участвуют.
Портал и локальная embedding-модель не вызываются; платформенные утверждения
без документации портала с версией запрещены инструкцией ревью.

Пределы: 100 изменённых файлов, 200 000 байт diff, 120 000 символов JSON-контекста,
20 000 000 байт допустимых файлов корпуса; размер одного файла задаётся доменом.
Превышение предела останавливает запуск до запроса модели. Недоступные файлы,
бинарные данные, симлинки и отсутствие подходящих RAG-фрагментов видны как ограничения.
Литеральные учётные данные в поддерживаемых формах скрываются до доставки; это
эвристика, поэтому перед отправкой частного проекта нужно проверить его содержимое.

Код выхода 0 означает выполненное ревью, включая ревью с замечаниями. Код 1 означает
ошибку; после начала конвейера её этап сохраняется в отчёте. Каталог с прежними
результатами не перезаписывается. Модель возвращает JSON со списками potential_bugs,
architectural_problems и recommendations. Их структура, пути и строки проверяются кодом;
Markdown строится из данных. Непригодный JSON и незавершённый ответ — ошибка ревью.
Ревью не подтверждает сборку или тесты приложения.

## Подключение WebDavClient к GitHub Actions

1. Опубликовать ff.ai с reusable workflow `.github/workflows/pr-review.yml` и кодом
   исполнителя. Предлагаемый следующий тег — v0.32 после v0.31; номер согласуется
   с существующей строкой недели, но определяется историей релизов ff.ai.
2. Скопировать `examples/webdavclient-ai-review.yml` в
   `WebDavClient/.github/workflows/ai-review.yml`. После публикации можно закрепить
   `uses` на полном SHA коммита workflow вместо тега v0.32.
3. В личном GitHub-репозитории WebDavClient добавить `OPENCODE_API_KEY`:
   Settings → Secrets and variables → Actions → New repository secret.
4. Опубликовать workflow и открыть либо обновить PR внутри репозитория.
5. Настроить защиту основной ветки: успешный status check `AI review gate` от
   GitHub Actions обязателен для merge. Точное имя check с префиксом caller брать
   из фактического запуска. Существующие правила защиты сохраняются.
6. В PR прочитать комментарий ff.ai; в Actions текст также находится в Summary,
   `review.md` и `report.json` — в артефакте `ffai-pr-review-…`.

Caller запускается на opened/synchronize/reopened. Исполнитель и actions закреплены
на доверенных SHA. Анализ имеет только `contents: read`; отдельный job публикации
дополнительно имеет `pull-requests: write`. Caller разрешает это право как верхнюю
границу, credentials checkout не сохраняются.
PR используется как данные; его скрипты, зависимости, hooks и submodules не запускаются.
Параметры PR передаются через окружение, без подстановки в shell-код.
Для PR из fork GitHub обычно не передаёт секреты: такой запуск сохраняет
`status: not_run`, сообщает об отсутствии ключа и завершается ненулевым кодом.
Это ограничение не обходится через `pull_request_target`.
См. [документацию GitHub о PR-событиях](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows).

Workflow сохраняет артефакты и при ошибке после создания отчёта. Если запуск
остановился до конвейера, например при checkout, подробности находятся в Actions log.
Успешный результат публикуется в один комментарий github-actions[bot] с маркером
ff.ai, head SHA и ссылкой на run. Повторное ревью обновляет его; пользовательские
комментарии сохраняются. Если head изменился, старый результат не публикуется.
Длинный комментарий явно сокращается со ссылкой на полный артефакт.
Ошибка публикации видна в отдельном job и не удаляет артефакты.

Баги и архитектурные проблемы создают красный `AI review gate` и блокируют merge.
Рекомендации без таких проблем не блокируют. После исправлений нужен новый успешный
прогон, который обновляет комментарий и снимает блокировку. Ошибки API, отсутствующий
ключ и неуспешная публикация также не дают зелёного gate. Рекомендации не применяются
автоматически, merge остаётся действием пользователя.

## Сценарий демо

1. Создать временную копию отслеживаемых файлов WebDavClient, скрыть литеральные
   учётные данные и завести собственную git-историю копии. Исходный проект не менять.
2. Внести небольшую регрессию в существующую операцию; показать base/head и diff.
3. Показать caller workflow, PR-триггер и вызов reusable workflow.
4. Запустить тот же `ff-ai-review.py` с настоящей моделью и изолированными путями FFAI.
5. Показать этапы, RAG-фрагменты исходников и документации с путями и строками.
6. Открыть три раздела ревью, сопоставить найденную регрессию с diff,
   показать источники и реальные метрики.
7. После разрешённой публикации отдельно подтвердить запуск на PR ссылкой на
   фактический Actions run. Локальный запуск не выдавать за исполненный GitHub Action.

Перед записью выполнить doctor и сухой прогон. Результат записи —
`videos/day32-demo.mp4`, черновики — `videos/day32-README-draft.md` и
`videos/day32-release-notes.md`. URL видео добавляется только после загрузки.

## Проверенный локальный результат

Полный локальный набор без network: 1 488 passed, 11 deselected за 325,46 с.
actionlint, shell-синтаксис workflow и строгая проверка спецификаций прошли.
Запись экрана проверена по ключевым кадрам, длительность — 104,40 с.
Ревью действительно нашло внесённую регрессию. Модель deepseek-v4.1-flash:
7 257 входных и 3 655 выходных токенов, 10 912 всего, запрос 34,53 с,
расчётная стоимость $0,0065631. Отчёт и ответ сохранены в
`videos/day32-recorded-report.json` и `videos/day32-recorded-review.md`.

Во время локальной записи оригинальный WebDavClient не изменялся.
После разрешённого подключения caller опубликован в основной ветке example,
GitHub Secret настроен. Первый реальный [PR-прогон](https://github.com/ivanshchitov/WebDavClient/actions/runs/38401379321)
подтвердил доставку кода и документации и обнаружение регрессии в
[демонстрационном draft PR](https://github.com/ivanshchitov/WebDavClient/pull/1).
После этого пользователь добавил требования комментария и блокирующего gate;
их итоговые красный и зелёный прогоны проверяются отдельно.
