# Домен `aurora-qt5`: разработка приложений под ОС Аврора (Qt 5.6)

Первый пакет домена (см. `docs/domains.md`). Всё ниже — данные пакета `domains/aurora-qt5/`;
ядро ff.ai этих слов не знает.

## 1. Область применимости

Четыре уровня, по ним же работает гейт отказа:

| Уровень | Содержание | Поведение |
|---|---|---|
| **1. Целевой репозиторий** | код, `.pro`/`CMakeLists.txt`, `.spec`, QML, ресурсы, история git, сборка и тесты именно этого проекта | отвечает и работает с кодом |
| **2. Платформа** | OC Аврора, Qt 5.6, QML и Aurora.Controls/Silica, публичные API, разрешения, `.spec` и RPM, Аврора SDK, `sfdk`/psdk, подпись, установка и запуск на устройстве, эмулятор | отвечает **только по документации портала** со ссылкой на раздел |
| **3. Смежное** | общий C++/Qt 5, системы сборки (qmake, CMake, ninja), алгоритмы, отладка — если нужно для уровней 1–2 и не противоречит платформе | отвечает, помечая, что факт не платформенный |
| **4. Вне области** | всё остальное: другие ОС и мобильные платформы, веб-разработка, чужие предметные области, бытовые и общие вопросы | фиксированный отказ с объяснением |

Пограничные случаи, как их решает домен:

- «Как собрать пакет для Android?» → отказ по уровню 4 (другая платформа), даже если проект собирается под Аврору.
- «Что такое `moc`?» → уровень 3 (общий Qt), допустим как пояснение к уровню 2.
- «Сделай то же самое под Sailfish OS» → отказ: вне области; в коде при этом допустим модуль `Sailfish.Silica` из таблицы публичных API — отказ касается платформы, а не идентификатора.
- «Перепиши проект на Qt 6» → отказ по инварианту 3 с объяснением, чем именно Qt 6 противоречит платформе.

### Локальная среда (проверено на рабочей машине)

Среда — такая же часть домена, как и документация: правило «ответ называет версию» относится и к SDK.

**Обозначения путей.** Используются шаблоны одного вида, `/path/to/...` (полные пути конкретной
машины не пишутся): `/path/to/AuroraOS` — установка Аврора SDK (по умолчанию `$HOME/AuroraOS`),
`/path/to/AuroraPlatformSDK` — установка Platform SDK (по умолчанию `$HOME/AuroraPlatformSDK`),
`/path/to/auroraos-regular-keys` — материал подписи (по умолчанию `$HOME/.auroraos-regular-keys`),
`/path/to/ssh/config` — конфигурация SSH пользователя (по умолчанию `$HOME/.ssh/config`).

| Что | Состояние | Следствие |
|---|---|---|
| Аврора SDK | `/path/to/AuroraOS`, `sfdk` — в `/path/to/AuroraOS/bin` (**не в PATH**), версия `5.1.5.105-mb2`, цикл Beta | искать `sfdk` в PATH, затем в `/path/to/AuroraOS/bin`; версию SDK называть в ответах о сборке |
| Цели сборки | `AuroraOS-5.1.5.105-MB2-{aarch64,armv7hl,x86_64}` и снимки `.default` | `aarch64`/`armv7hl` — устройства, `x86_64` — эмулятор; снимки отбрасываются |
| Platform SDK | отсутствует (`/path/to/AuroraPlatformSDK` нет) | инструмент сборки один, выбор автоматический; ветка `psdk`/`mb2` на этой машине неиспользуема |
| Эмулятор | `VBoxManage` установлен, каталог `emulator` внутри `/path/to/AuroraOS` | запуск на эмуляторе возможен |
| Устройства | в `/path/to/ssh/config` есть `aurora-engine` (mersdk), `aurora-emulator` (defaultuser), `-root`-варианты и версионный `aurora-emulator-4.1` | адрес по умолчанию берётся оттуда, а не угадывается |
| Ключи подписи | `/path/to/auroraos-regular-keys/{regular_key.pem,regular_cert.pem}` | Regular-профиль доступен; содержимое ключей не печатается никогда |
| Инструменты сборки | `rpmbuild`, `qmake`, `cmake`, `ninja`, `gdbus`, `scp`, `ssh` в PATH; `mb2`, `rpmsign-external`, `rpm-validator` — только **внутри** движка SDK | подпись, валидация и `mb2` вызываются через `sfdk engine exec`/среду сборки |
| Хост-система | macOS (darwin) | `%defattr` в `%files` **обязателен**, иначе ошибка валидации (требование портала для macOS и Windows) |
| Python | 3.14.8 | пол 3.10+ (из-за пакета `mcp`) соблюдён |

**Рассинхрон версий — штатная ситуация, а не авария.** Установлен SDK 5.1.5, а документация
портала по умолчанию — 5.2.1. Разница видна на практике: запуск Qt-тестов портал описывает для
SDK 5.2.1+ и устройства с ОС 5.2.0+, а в 5.2.0 добавился манифест совместимости
(`rpm/manifest.json`). Поэтому ассистент обязан: назвать версию документации в ответе,
сравнить её с версией установленного SDK и, если документ новее, предупредить и поискать
раздел нужной версии (`search` с параметром `version`).

## 3. Источники знаний (корпуса)

| Корпус | Что это | Как читается |
|---|---|---|
| Код репозитория | файлы целевого проекта | локальный индекс (RAG) |
| Документация портала | `docs`, `ext_docs`, `articles`, `release_notes`, `news`, `qa` | MCP-сервер `dev-aurora`: `search` → `get_document`, для примеров `search_code` → `get_code_source` |
| Проектные артефакты | `.spec`, `.pro`, CMake, `.desktop`, ресурсы | локальный индекс |

**Сервер `dev-aurora`.** Транспорт — remote (streamable HTTP), адрес `https://developer.auroraos.ru/api/mcp`,
токен не нужен; инструменты: `search`, `get_document`, `get_doc_versions`, `search_code`,
`get_code_source`, `get_ext_tools_list`, `get_portal_info`, `echo`. Прямой `GET` этого адреса
браузером отдаёт `403` — признак MCP-эндпоинта, а не ошибки доступа; подключение проверяется
реальным вызовом инструмента (`echo`), как того требует правило реестра серверов.

**Идентификаторы источников.** Для фрагмента портала `chunk_id` — путь документа
(`doc/sdk/tools/mb2`), `source` — `developer.auroraos.ru`; для фрагмента кода — `path:L10-L40`.
Платформенное утверждение без такого идентификатора не принимается (инвариант 10).

## 4. Правила работы с документацией портала (инструкции промпта)

Прямая проекция алгоритма проверки достоверности, потому что Аврора — закрытая и версионируемая
платформа: догадка по Sailfish или по настольному Qt даёт правдоподобный, но неверный ответ.

1. **Никогда не отвечать по памяти о платформе.** Сначала `get_doc_versions` — если пользователь
   назвал версию устройства или SDK, искать в ней, иначе в `latest`, и **в ответе называть версию**.
2. **Выбирать конкретный раздел**, а не `all`: `docs` — как работает API; `qa` — «у меня не
   работает»; `release_notes` — «в какой версии появилось»; `articles` — руководства;
   `ext_docs` — сторонние инструменты (сначала `get_ext_tools_list`, чтобы знать, что покрыто).
3. **Полный текст, а не сниппет**: `get_document(path, index)` для лучших попаданий; для Q&A
   сниппетов достаточно.
4. **Код — только по запросу реализации**: `search_code`, при нехватке — `get_code_source(url)`.
5. **Не выдумывать пути и имена**: `path` берётся строго из результатов поиска.
6. **Показывать источник** каждого платформенного утверждения (раздел + путь/URL).
7. **Не называть ОС «Sailfish»** в ответе: терминология портала — «ОС Аврора». Идентификаторы
   кода (`Sailfish.Silica`, `libsailfishapp`) при этом не переписываются.
8. **Нет ответа в документации** — сказать честно, показать, что искали, и предложить обращение
   в поддержку вендора; пробел не заполняется догадкой.
9. **Сервер недоступен** — сообщить «документация портала недоступна, ответить по ней не могу»,
   показать, как подключить, и остановиться; не подменять документацию рассуждением.
10. **Аргументы команд зависят от версии SDK** — сомнение проверять через `search`/`get_document`,
    а не по памяти.
11. **Сравнивать версию документа с локальной средой.** Документация по умолчанию — 5.2.1,
    установленный SDK здесь — 5.1.5; если документ описывает поведение более новой версии
    (например, запуск Qt-тестов с SDK 5.2.1+ или манифест совместимости с ОС 5.2.0), это
    произносится вслух, и при необходимости ищется раздел нужной версии.

## 5. Инварианты домена

Проверяются и в тексте ответа, и в аргументах инструментов. Правила ниже **дополняют** базовые
инварианты (`docs/design.md` §6), а не заменяют их. Формат — как в пакете: номер, правило,
запрещённые стемы (для машинной проверки), источник.

| # | Правило | Стемы | Источник |
|---|---|---|---|
| 1 | Только модули и библиотеки из таблицы публичных API | проверка по списку модулей и `%{_datadir}`-зависимостей | `reference/public_api` |
| 2 | QtWidgets не используется | `qtwidgets`, `QT += widgets`, `QApplication` | `reference/public_api` → «Недоступные зависимости» |
| 3 | Только Qt 5.6: никаких Qt 6 и его CMake-идиом | `qt6`, `qt_add_dbus_interface`, `extra-cmake-modules`, `ecm_feature_summary` | `platform/architecture/qt`, `guides/build_bluez` |
| 4 | Состав SDK, целей и тулинга не меняется | `sfdk maintain`, `SDKMaintenanceTool`, `sdk-assistant target create` | справка конвейера, `sdk/tools/…` |
| 5 | `.spec` соответствует требованиям: `Name` совпадает с именем файла, `Epoch` не используется, `%files` называет конкретные файлы, `%defattr` указан при сборке на macOS/Windows | — (проверка структуры файла) | `guidelines/rpm_requirements/spec_requirements` |
| 6 | На устройство ставится только подписанный пакет; подпись проверяется по строкам вывода `rpmsign-external dump`, а не по коду возврата (`verify` требует корневого CA и не используется) | `rpmsign-external sign` перед установкой | `sdk/tools/rpmsign_external` |
| 7 | Разрешения объявлены в обязательном разделе `[X-Application]` файла `.desktop` и совпадают с используемыми API | сверка с таблицей разрешений и профилем безопасности | `guidelines/rpm_requirements/desktop_requirements`, `reference/public_api` |
| 8 | Ключи и сертификаты подписи не попадают в репозиторий и в вывод | `-----begin`, `regular_key`, `*.pem`, `*.key` | справка конвейера (материал подписи) |
| 9 | `.gitignore` и чужие файлы не переписываются; состояние инструмента — в `.aurora/` через `.git/info/exclude` | правки `.gitignore` при записи состояния | справка конвейера, «Состояние» |
| 10 | Платформенный факт приводится со ссылкой на документацию портала | — (проверка цитаты) | этот документ, §4 |

Дополнительно фиксируются ловушки платформы (в промпте и подсказках, без машинной проверки):

- `rpm -q` отвечает «не установлен» и для приложения, поставленного через APM, — проверять нужно
  через `ru.omp.APM.GetPackage`; установленные через APM приложения не видны базе `rpm`;
- валидатор RPM вызывается **автоматически при установке**, и пакет, не прошедший валидацию,
  установить нельзя; отдельный его вызов в среде сборки нужен, чтобы узнать причину заранее;
- при нескольких `.spec`-файлах среда сборки не выбирает файл сама и падает с
  «Multiple spec files found — please select one»: путь указывается явно;
- подпись запрашивает кодовую фразу интерактивно; для неинтерактивного вызова она передаётся
  переменной `KEY_PASSPHRASE` — иначе шаг подписи зависает на вводе;
- путь из макроса `%{_bindir}` не переносится целиком: указывать конкретный исполняемый файл.

## 6. Инструменты домена

Белые списки (всё вне них отклоняется до выполнения):

| Назначение | Разрешено |
|---|---|
| Чтение состояния SDK | `sfdk tools list`, `sdk-assistant list` (внутри chroot) |
| Сборка | `sfdk config target=<цель>`, `sfdk build <проект>`, `mb2 -t <цель> -o build_<arch>/RPMS build` |
| Подпись и проверка подписи | `rpmsign-external sign -k <ключ> -c <сертификат> <rpm>` (кодовая фраза — через `KEY_PASSPHRASE`, иначе интерактивный ввод), `--force` для замены подписи, `rpmsign-external dump <rpm>` для просмотра подписи; всё внутри среды: `sfdk engine exec …`. `verify` не используется — требует корневого сертификата CA |
| Проверка пакета | `rpm-validator` (в среде сборки или IDE; при установке вызывается автоматически, и пакет без валидации не установится) |
| Тесты | сборка цели с тестами и запуск Qt Test — требует SDK 5.2.1+ и устройства с ОС 5.2.0+; при локальном SDK 5.1.5 шаг недоступен, о чём сообщается вместо ложного «тестов нет» |
| Доставка на устройство (после отдельного подтверждения) | `scp` в каталог загрузок пользователя на устройстве, `gdbus` → `ru.omp.APM.Install` / `Remove` / `GetPackage`, запуск `sailjail /usr/bin/<APP>` по SSH |

Запрещено безусловно: `sfdk maintain`, `SDKMaintenanceTool`, `MaintenanceTool`,
`sfdk tools install|update|remove|create`, `sdk-assistant target create|remove|update`,
`sdk-assistant tooling` — установка и обновление SDK, целей и тулинга остаются ручной работой
пользователя (инвариант 4).

Каталог сборки — всегда `<проект>/build_<arch>/`, артефакты — `build_<arch>/RPMS/`; идентификатор
приложения — ключ `Name` из `.spec` (`rpm/*.spec`, затем `*.spec` в корне), он же путь запуска
`/usr/bin/<Name>`.

## 7. Детерминированные проверки (валидация задачи)

Выполняются кодом, без модели, и попадают в вердикт проверки задачи. Все перечисленные проверки
опираются на документы портала, а не на догадки:

- **Сборка цели выбранной архитектуры**: ненулевой код — замечание с последней строкой вывода
  (не «не собралось», а причина).
- **Зависимости и модули против таблицы публичных API** (инварианты 1–2): сверяются `BuildRequires`,
  `Requires`, `QT +=`, строки `import` в QML и список разделяемых библиотек; QtWidgets —
  отдельное замечание с причиной из документации.
- **Qt 6-идиомы** в `.pro`/`CMakeLists.txt`/`main.cpp` (инвариант 3): `qt6`, `qt_add_dbus_interface`,
  `extra-cmake-modules`, `ecm_feature_summary`.
- **Структура `.spec`** (инвариант 5): обязательные `Name`, `Version`, `Release`, `Summary`,
  `License`, `URL`, секции `%files`; `Name` совпадает с именем файла; `Epoch` отсутствует;
  в `%files` — конкретные пути, а не каталог `%{_bindir}` целиком; при сборке на macOS/Windows —
  наличие `%defattr`.
- **Файл `.desktop`** (инвариант 7): обязательный раздел `[X-Application]`, ключи `Icon`, `Exec`,
  `Name`, `Type=Application`, `X-Nemo-Application-Type=silica-qt5`; список `Permissions` сверяется
  с используемыми API, а сами значения — со списком разрешений и профилем безопасности.
- **Подпись пакета** (инвариант 6): `rpmsign-external dump` — решение по строкам
  `Signature:`/`Key ID:`, а не по коду возврата (`dump` завершается нулём и для неподписанного
  пакета); иной вывод — «проверить не удалось», а не «пакет не подписан».
- **`rpm-validator`** по собранному пакету (в среде сборки): это та же проверка, что выполняет
  устройство при установке, поэтому её результат предсказывает установку.
- **Неоднозначность выбора**: несколько `.spec` или несколько подходящих целей — не угадывать,
  а вернуть вопрос; одна подходящая цель — взять её и сказать, откуда она взялась.

## 8. Память и профиль домена

Правила маршрутизации реплик (образцы → слой, категория, ключ): `цель` — «хочу добавить экран»,
`ограничения` — «не используем Qt Widgets», «только aarch64»; долговременная память — `стек`
(«проект на qmake», «SDK 5.1.5»), `решения` («подпись Regular-ключами»), `знания`
(«устройство 192.168.2.15»).

Разделы профиля: цель сборки по умолчанию (архитектура), инструмент сборки (`sfdk`/psdk),
ключи подписи (путь, без содержимого), уровень владения Qt/QML, стиль ответов по документации
(«всегда со ссылкой», «кратко/подробно»). Значения профиля подчинены настройкам и свежей реплике,
но не отменяют инвариантов.

## 9. Контрольный набор (`scenarios.md`)

Демонстрация и регрессия домена, каждый пункт — с ожидаемым исходом:

1. «Как в Авроре получить геопозицию?» → ответ по `docs`/`cpp_api` со ссылкой и версией.
2. «Можно ли использовать QtWidgets?» → отказ по инварианту 2 с причиной из документации.
3. «Собери пакет под aarch64» → конвейер: цель, сборка, `build_<arch>/RPMS/`, подпись.
4. «Почему `rpm -q` говорит, что приложения нет?» → разбор ловушки APM.
