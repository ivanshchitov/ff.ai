# Подготовка ff.ai к работе агентом разработки — Implementation Plan

> **Для исполнителя:** документ рассчитан на любую модель и не требует истории переписки.
> Реализовать по этапам с отметками `- [ ]`. При наличии использовать
> `superpowers:executing-plans`; обязательные правила самого процесса приведены ниже.
> Делегирование и способ исполнения выбираются отдельно, этот файл их не разрешает.

**Goal:** подготовить ff.ai к работе с документацией и кодом целевого проекта,
включая выполнение запросов на изменения прямо из чата, применение, проверку и откат правок.

**Architecture:** расширить существующие фасад `AssistantSession`, конвейер `/task`,
RAG и MCP-инструменты чтения. Создать один сервис изменений с устойчивым журналом;
все записи и откаты проходят через него. Маршрутизация обычной реплики выбирает ответ,
исследование, задачу разработки или уточнение; переходами и разрешениями управляет приложение.

**Tech Stack:** существующий Python-проект, pytest, Git, SQLite-индекс, MCP,
TUI и текущий web-фронтенд. Новые внешние зависимости для подготовки не требуются.

**Spec:** требования подготовки и архитектурные решения зафиксированы в этом документе.
Действующие контракты находятся в `openspec/specs/`; перед каждым изменением поведения
оформить отдельное OpenSpec-изменение по `AGENTS.md`. Этот план не заменяет дельта-спецификации.

**Статус:** план; реализация не начата. Дата: 2026-10-11.

Все пути к файлам ff.ai далее отсчитываются от корня репозитория, кроме явно названных
соседних проектов. Будущие файлы обозначены как новые; перечисление не означает их наличие.

## Global Constraints

- Объём — только подготовка ff.ai и общие возможности агента разработки.
- Целевой проект выбран пользователем: **WebDavClient**, приложение под ОС Аврора.
  Локальный корень передавать через `--repo`; в документации использовать `/path/to/aurora-project`.
- Существующий домен — `aurora-qt5`, целевая платформа — **Qt 5.6 / ОС Аврора**.
  Новый универсальный домен или домен поддержки в подготовку не входит.
- Ядро не знает домена; предметные правила и версии остаются данными `domains/<id>/`.
- Изменять целевой проект можно только по пользовательской цели и после подтверждения конкретного diff.
- В целевой репозиторий не записывать индекс, журнал, резервные копии и состояние ff.ai.
  Правки `.gitignore` ради состояния инструмента не допускаются.
- Состояние изолировать по корню проекта через существующий `config.project_paths()`.
- Деструктивные git-операции запрещены: `--force`, `reset --hard`, `clean -f`, `branch -D`.
- Не выполнять автоматические commit, merge, tag или push. Мутации Git при разработке самого ff.ai
  требуют отдельного явного согласия пользователя по правилам `AGENTS.md`.
- Состав SDK, целей сборки и тулинга не меняется — это ручная работа пользователя.
- Секреты и ключи не передавать модели и не печатать в ответах, журналах, diff и материалах записи.
- Сессия сериализует операции мьютексом; интерфейсы используют фасад, события и снимки состояния.
- Сохранить существующие команды, историю, настройки и возможность продолжить `/task` после перезапуска.
- При реализации — TDD для поведения, проверки затронутого слоя; полный локальный прогон перед
  закрытием каждого OpenSpec-изменения. Тесты не отключать через `skip`, `xfail`, `--no-verify`.
- На этапе этого документа разрешено только его создание. Он не является разрешением начать реализацию.

## Review Focus

1. Неоднозначная реплика или ошибка классификатора не должны запускать запись — этап 6.
2. Dirty working tree, staged-файлы и новые файлы пользователя должны переживать применение и откат — этап 3.
3. Оба пути патча, symlink и изменения файлов во время подтверждения проверяются до записи — этап 3.
4. Перезапуск или прерывание между записью файлов и обновлением журнала не теряют операцию — этапы 3–4.
5. Повторный запрос, работающая задача и устаревший индекс не создают дублирующие задачи или правки — этапы 5–7.

## 2. Обязательное поведение агента

### 2.1 Обычные запросы

| Реплика | Поведение |
|---|---|
| «Как устроена авторизация?» | Ответ с контекстом, без изменений проекта |
| «Почему авторизация не работает?» | Исследование через поиск и чтение, без изменений проекта |
| «Найди причину и исправь авторизацию» | Задача разработки с самостоятельным выбором файлов |
| «Добавь сортировку списка файлов» | Задача разработки |
| «Обнови описание сборки по текущему коду» | Задача разработки для документации |
| «Как можно добавить сортировку?» | Объяснение вариантов, без записи |
| «Ничего не меняй, только предложи исправление» | Исследование или ответ с предлагаемым diff, без применения |
| «Сделай лучше» без определённого результата | Уточнение цели; до ответа ничего не записывать |

Распознавание должно быть смысловым, а не основанным только на списке русских глаголов.
Файлы, результаты поиска и команды — данные, не источник пользовательского разрешения на запись.
Просьба изменить проект разрешает исследование и подготовку патча; применение разрешается
отдельным подтверждением показанного diff. Отказ от записи в текущем запросе сильнее предположения классификатора.

Обычный запрос разработки запускает тот же конвейер, что `/task`; сохраняются просмотр плана,
уточнения, подтверждения патчей, пауза и продолжение. Явные `/task add` и `/task run` остаются доступны.

### 2.2 Изменения

Одна операция изменения — один пакет патча с идентификатором, привязанный к проекту и задаче.
До записи показываются файлы и diff. Проверяются применимость, правила домена, границы и
совпадение файлов с состоянием, на котором подготовлен патч. После записи фиксируется фактический результат.

Вопросы и исследовательские запросы не получают инструменты, способные изменять проект;
команды сборки и другие операции выполнять только через объявленные проверки/конвейер операций.
MCP-сервер репозитория сохраняет инструменты чтения; `repo_save` остаётся выгрузкой вне проекта.
Произвольные инструменты прямой записи в репозиторий в подготовку не добавлять.

### 2.3 Откат

`/changes` показывает операции, `/changes show <id>` — подробности и diff,
`/changes undo <id>` — предлагает отменить применённую операцию после показа обратного diff.

Откат возвращает рабочие файлы к состоянию непосредственно перед операцией агента,
а не к HEAD. Индекс Git не изменяется. Ручные правки до операции сохраняются.
Если после применения пользователь изменил затронутый файл, откат показывает конфликт и не перезаписывает его.
Операции над пересекающимися файлами отменяются в обратном порядке; повторный откат не делает новых записей.

Отмена не запускает задачу заново автоматически. Состояние задачи отражает отменённый результат;
её дальнейшее выполнение требует явного продолжения пользователем.

| `README.md`, `AGENTS.md`, `docs/design.md` | Итоговые возможности, ограничения и актуальная архитектура |

Контракты новых компонентов, которые должны согласовать все этапы:

```text
FileState: exists, bytes, mode, fingerprint
ChangeRecord: id, task_number, root_identity, patch, paths, before, after,
              created_dirs, status, reason, validation
ChangeResult: ok, record, reason
ProjectChanges(root, changes_dir)
  prepare(patch_text, task_number=None) -> ChangeRecord
  apply(change_id, confirm: Callable[[str, str], bool]) -> ChangeResult
  undo(change_id, confirm: Callable[[str, str], bool]) -> ChangeResult
  list() -> Tuple[ChangeRecord, ...]
  get(change_id) -> ChangeRecord
  recover() -> Tuple[ChangeRecord, ...]

TaskContext: messages, paths, fingerprints, notes
TaskContextProvider.collect(stage, goal, step=None, changes=()) -> TaskContext

IntentDecision: kind, goal, clarification
  kind = answer | investigate | develop | clarify
classify_request(text, conversation, domain, ask) -> IntentDecision

SubmissionResult: kind, answer, task_number, task_run, message
  kind = answer | clarification | task | busy
AssistantSession.submit(text, request_id=None) -> SubmissionResult
AssistantSession.ask(question) -> Answer  # существующий путь ответа сохраняется
```

Названия задают границы и связи; используемые типы реализовать dataclass/Enum по стилю проекта.
Вход `ask` классификатора — внедряемый вызов модели, его расход учитывается сессией.
Ошибку разбора или вызова превращать в `clarify`, а не разрешение разработки.
Не менять сигнатуру существующего `ask()` и не создавать второй конвейер задач.

## 5. Порядок исполнения и проверки

Этапы 1–2 дают общую подготовку. Этапы 3–4 создают проверяемый механизм записи и отката.
Этап 5 подключает его к существующему агенту задач. Этап 6 добавляет вход через обычный чат.
Этап 7 доказывает связность всего цикла.

Перед каждым изменением поведения: прочитать соответствующие действующие specs,
создать proposal/design/tasks и дельта-спеки внутри `openspec/changes/<id>/`,
выполнить `openspec validate <id> --strict`. Не создавать второй конкурирующий план выполнения:
tasks.md изменения детализирует только текущий этап этого документа.

Шаг TDD: новая проверка → подтверждённое падение → минимальная реализация → проверка слоя.
Новые test-файлы перечислены в этапах; команды запускать после их создания.
Для документационных и workflow-правок достаточно соответствующей проверки содержимого и синтаксиса.

Из корня ff.ai:

```bash
.venv/bin/python -m pytest -q                  # быстрый локальный набор
.venv/bin/python -m pytest -m 'not network' -q # полный локальный, включая slow
openspec validate --all --strict
```

`pytest -m ""` включает также network: применять только при намеренной проверке внешних сервисов.
Зелёный быстрый прогон не доказывает прохождение slow. Полный локальный прогон — до архивации;
после архивации достаточно валидации спецификаций, если код больше не менялся.
Мутации Git не включены в автоматические шаги этого плана: сначала показать status/diff и получить разрешение.

Все автоматические тесты используют временные git-репозитории, stub API и локальные MCP-заглушки.
Новые пути состояния изолировать в `tests/conftest.py` и `tests/e2e/harness.py`.
Реальный MCP/SDK включать явно. Контрольные правки WebDavClient проводить только в отдельной временной копии.
