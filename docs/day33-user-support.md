# День 33: ассистент поддержки пользователей

Источник требований: `../ai-advent-challenge-9/week7/day33/README.md`.
Контекст недели: `../ai-advent-challenge-9/week7/README.md` и дни 31–32.
Решение — ff.ai, продукт примера — WebDavClient.

## Критерии и реализация

Ассистент отвечает на вопросы о продукте, использует FAQ/документацию через RAG,
учитывает пользователя и тикет из JSON через настоящий MCP по stdio.
Формат сдачи — видео + код. Конвейер последовательный:
вопрос → выбранный тикет MCP → локальный RAG → модель → ответ с источниками и метриками.
Субагенты не являются обязательным требованием дня.

Домен `product-support` выбирается явно и также определяется по `.support-product`.
Прежний домен разработки помечен default, чтобы добавление пакета не меняло запуск
в проектах без маркеров. Предметные инструкции остаются данными домена.

## Запуск

```bash
cd /path/to/ff.ai
cp -R examples/support-webdavclient /path/to/support-project
git init /path/to/support-project
./ff-ai.py --repo /path/to/support-project --domain product-support
```

Для web добавить `--web`. Пример содержит копию руководства из WebDavClient
и FAQ, составленный по руководству и коду. Исходный commit указан в README примера;
исходный WebDavClient не меняется. Имена, тикеты и адреса example.test вымышленные.

```text
/rag-code index
/support TICKET-101 Почему не получается войти и что мне сделать?
/support TICKET-102 Почему не получается войти и что мне сделать?
/support TICKET-103 Что выбрать, чтобы файл остался на сервере?
/rag-code trace
/usage
```

Команда поддержки получает FAQ и документацию через существующий корпус `/rag-code`.
Она выбирает baseline с настройками before/after сессии и восстанавливает настройки
поиска после запроса. Портал, автовыбор действий, классификатор разработки, память,
профиль и прежний диалог в запросе не участвуют. Ответ поддержки не добавляется в
историю, расход учитывается в сессии. Следующий тикет получает собственный контекст.
TUI и web показывают одинаковые ответы, источники, метрики и явные ошибки.

## MCP и данные

`domains/product-support/support.json` задаёт относительный `data_path` и имя `tool`.
По умолчанию данные читаются из `support.json` выбранного проекта через
`support_get_ticket(ticket_id)`; `support_health` проверяет доступность сервера.
Инструменты имеют аннотацию только чтения. Сервер перечитывает JSON при каждом вызове.

Схема источника: объект с `schema: 1`, списками `users` и `tickets`.
У каждой записи уникальный `id`; `ticket.user_id` ссылается на существующего пользователя.
У пользователя доставляются id/name/experience; у тикета — id/user_id/status/subject/
description/error_code/product_version/provider. Остальные поля исключаются.
Лимиты: файл 1 MiB, результат 16 000 символов. Симлинки и выход за границы проекта
отклоняются; каталоги открываются по дескрипторам без следования симлинкам.
Пароли и токены не нужны; распознаваемые секреты в свободном тексте скрываются
существующим механизмом. Это эвристика: частные документы и описания оператор
проверяет перед подключением. Пример не содержит реальных учётных данных.

Неизвестный тикет, недоступный файл, ошибочная схема и сбой MCP прекращают запрос
до модели. Отсутствующий/stale индекс или пустой поиск называются явно; прежние
фрагменты после ручного изменения документа не используются. Сбой модели — ошибка
запроса. Приложение не изменяет продукт или тикеты и не объявляет проблему исправленной.
Выбор тикета предназначен для локального оператора; многопользовательской проверки
прав доступа в этом примере нет.

## Сценарий демо

1. Показать FAQ, руководство и вымышленный JSON; собрать индекс.
2. TICKET-101: Яндекс.Диск, диагностический expired_token, переход к повторному входу.
3. TICKET-102: обычный WebDAV, 404, адрес сайта отличается от полного адреса,
   указанного администратором. Задать тот же вопрос, показать другой ответ.
4. TICKET-103: выбрать Скачать, чтобы оригинал остался на сервере;
   объяснить отличие от Переместить на устройство по руководству.
5. Обновить второй тикет: правильный адрес помог, статус resolved, прежний код ошибки
   убран. Спросить об обновлении списка — ожидается Обновить папку, а не исправление входа.
6. Запросить TICKET-999: явная ошибка без вызова модели.
7. Показать источники RAG, трассировку и фактический расход.

Ошибки заданы данными тикетов, не выдаются за воспроизведённые на настоящих серверах.
Ответы для записи должна дать настоящая модель, их полезность проверяется вручную.

Автоматизированный прогон из корня ff.ai:

```bash
.venv/bin/python scripts/day33_demo.py --output videos/day33-live-run.json
.venv/bin/python scripts/day33_demo.py --visible --output videos/day33-tui-run.json
```

Скрипт создаёт временную git-копию примера и переопределяет все пути состояния FFAI.
Первый режим — сухой прогон фасада; второй запускает настоящий ff-ai.py в TUI.
Он ждёт новые строки метрик, а не эхо команды или фиксированную паузу ответа.
Существующий файл результата не перезаписывается. Сохранение отчёта не является
записью экрана. Для видимого режима временный каталог сохраняется до остановки рекордера;
после неё удалить только каталог, созданный этим запуском.

Видео записано пользователем вручную и подтверждено готовым. По его указанию
запись не разыскивается и повторно не проверяется. Сценарий демо сохранён без изменений.
Черновики сдачи и release notes расположены в videos/. URL видео добавляется после
загрузки, ссылка на релиз — после создания тега.
