# ff.ai — план реализации

Фаза = одно изменение OpenSpec (`openspec/changes/<id>/`) и один проверяемый инкремент:
сначала падающий тест, минимальный код, тест слоя, полный `pytest`, `openspec validate --strict`,
`archive --yes`, тег релиза. Каждая фаза заканчивается демонстрацией на живом приложении.

Обозначения: **M** — минимум, без которого это не ассистент по разработке под Аврору; **П** —
паритет с челленджем (техники дней 1–27 в dev-домене).

Домен по умолчанию — `aurora-qt5` (ОС Аврора, Qt 5.6): `docs/domains.md`,
`docs/domain-aurora-qt5.md`.

## P0. Каркас, фасад сессии, пакет домена (M)

**Объём.** Репозиторий и точка входа `ff-ai.py` (перезапуск в `.venv`); `core/session.py`
(`AssistantSession`, события, мьютекс); `core/config.py` с префиксом `FFAI_*`; `--repo`/
`FFAI_REPO_ROOT` с проверкой git-корня; `core/domains.py` — загрузка, проверка схемы,
автоопределение и снимок пакета домена; пакет `domains/aurora-qt5/` (область применимости,
промпты роли и отказа, инварианты, память, профиль, инструменты, корпуса, проверки, сценарии);
перенос слоёв донора без домена (API-клиент, настройки ответа, стратегии контекста и сжатие,
история, расход, панели-редьюсеры, чтение клавиш) и самого агента — **без** доменных подсистем
донора (маршрутизация памяти, профиль, инварианты, задача, инструменты, RAG, расписание: каждая
приходит своей фазой); TUI-цикл с `/commands`, `/domain`, `/settings`, `/models`, `/context`,
`/usage`, `/clear`, `/exit`; формат `patch`; техпотолки и таймауты — из донора.

**Приёмка.** Вопрос по целевому репозиторию получает ответ; вопрос вне области (например
«как собрать это под Android») получает фиксированный отказ из пакета; `/domain` показывает
активный домен, версию платформы и найденные маркеры; правка `domains/aurora-qt5/` меняет
поведение без изменения кода; тест-инвариант «в `core/` и `ui/` нет идентификаторов из `domains/`»
зелёный; e2e не создаёт и не читает реальные файлы состояния.

**Демонстрация.** Запуск в корне проекта под Аврору → вопрос по коду → отказ на вопрос вне
области → `/domain`.

## P1. Корпус кода и индекс (M)

**Объём.** `core/code_index.py`: обход репозитория с учётом `.gitignore`, исключения (бинарные,
lock, vendor, крупные); стратегии `fixed` и `structural` с `path` и диапазоном строк; SQLite-схема
донора; `/docs index|status|compare`.

**Приёмка.** Индекс проекта под Аврору строится; `/docs compare` печатает два способа разбиения
с числом чанков и примером границ; ошибка сборки не затирает прежний индекс; индекс лежит в кэше
состояния (`/path/to/cache/ff-ai/path-hash/`), путь виден по `/docs status`, в репозитории не появляется
ничего.

**Демонстрация.** `/docs index` на проекте с C++/QML/spec, `/docs compare`, `/docs status`.

## P2. RAG по коду и обязательные цитаты (M)

**Объём.** Режимы `baseline`/`enhanced`, порог, `before/after`, `/docs tune`, `/docs trace`;
гейт «не знаю» при `no_matches`; инструкция цитат и детерминированная проверка `path:L10-L40`.

**Приёмка.** Контрольные вопросы по репозиторию: в каждом ответе источник и дословная цитата;
на теме, отсутствующей в корпусе, — «не знаю» без запроса к модели; смешанный вопрос (код +
платформа) на этой фазе отвечает по коду и честно говорит, что платформенная часть требует
фазы P4.

**Демонстрация.** «Где инициализируется модель списка?» → цитата `src/models.cpp:L40-L58`.

## P3. MCP: remote-транспорт и свой сервер (M)

**Объём.** `MCPClient` учится remote-транспорту (streamable HTTP) рядом с stdio; поле транспорта
в `MCPServerSpec` — данные; реестр учится соединять серверы, **объявленные пакетом домена**
(для `aurora-qt5` — `dev-aurora`, `https://developer.auroraos.ru/api/mcp`, без токена), и получает
собственный repo-сервер; `/mcp`, `/tool call`, `/tool auto`; проверка соединения вызовом `echo`,
а не только рукопожатием.

**Приёмка.** `/mcp` показывает оба сервера и их инструменты; `/mcp refresh` переустанавливает
соединение; недоступный сервер считается и печатает причину, сессия продолжается; тесты не ходят
в сеть (fake-серверы), `network`-тест проверяет реальный `dev-aurora` отдельным маркером.

**Демонстрация.** `/tool call` к серверу портала (`get_doc_versions`) и к своему серверу
(`repo_search`).

## P4. Документация портала как корпус ответа (M)

**Объём.** Платформенные ответы строятся только по документации портала: `get_doc_versions` →
выбор версии → `search` по конкретному разделу → `get_document` → ответ со ссылкой; правила §4
из `docs/domain-aurora-qt5.md` переносятся в промпт домена; цитата платформенного факта —
путь документа; отдельная строка источников с версией.

**Приёмка.** Вопрос «как в Авроре получить геопозицию?» → ответ со ссылкой на раздел и указанием
версии; вопрос «в какой версии появилось…» → `release_notes`; недоступный сервер → честное
«документация недоступна» без рассуждения по памяти; утверждение без ссылки не принимается
проверкой.

**Демонстрация.** Два-три платформенных вопроса, один из них — про версию.

## P5. Цепочка и оркестрация инструментов (M)

**Объём.** Перенос `mcp_tools`: каталог для запроса выбора, разбор одного инструмента / цепочки /
раунда, `$N`-подстановка (включая ссылки на строку), бюджеты результатов, маршрутизация шага
по серверам, журнальные строки по шагам.

**Приёмка.** Флоу «найти в коде → найти в документации → записать → прогнать проверку»
выполняется за один вопрос в песочнице; объёмы передачи видны; обрыв шага останавливает цепочку
и не попадает в данные; лимиты раундов и шагов соблюдаются.

**Демонстрация.** Запрос, который находит нужный API портала и правит QML-файл по документации.

## P6. Задача с детерминированной проверкой (M)

**Объём.** Перенос `task_state`/`task_pipeline`; артефакт — патчи файлов + `tasks/N-slug.md`;
**валидация — детерминированные проверки домена** (сборка цели, зависимости против публичных API,
Qt 6-идиомы, структура `.spec`, подпись) плюс модельное ревью диффа; пауза `p`/Ctrl+C, продолжение
после перезапуска.

**Приёмка.** Задача «добавь экран/поправь сборку» доходит до `Done` или до исчерпания попыток;
падение сборки переводит задачу в исправление, а не в `Done`; QtWidgets в предложенном патче
отклоняется детерминированной проверкой; после перезапуска прогон продолжается с сохранённого шага.

**Демонстрация.** Задача на живом проекте: план, патч, сборка, отчёт.

## P7. Конвейер сборки, подписи и запуска (M)

**Объём.** Операции конвейера по документации портала: выбор инструмента (`sfdk` или Platform SDK)
и цели по архитектуре, сборка в `build_<arch>/`, подпись `rpmsign-external` (кодовая фраза —
`KEY_PASSPHRASE`, а не интерактивный ввод), проверка подписи через `dump` (решение по строкам,
а не по коду возврата), доставка на устройство через APM, запуск `sailjail`; запрещённые
maintenance-команды отсекаются до выполнения; состояние выбора — в `.aurora/` через
`.git/info/exclude` (файлы репозитория не правятся); версия SDK называется в выводе, а рассинхрон
с версией документации проговаривается.

**Приёмка.** Полный цикл «сборка → подпись → установка → запуск» проходит с подтверждениями;
попытка `sfdk maintain` отклоняется; неподписанный пакет не устанавливается; отсутствие SDK или
устройства даёт понятную причину и нужный код выхода, прогон не падает.

**Демонстрация.** Полный цикл на устройстве или эмуляторе, включая отказ по maintenance-команде.

## P8. Память, профиль, инварианты домена (П)

**Объём.** Таблицы памяти и профиля из пакета домена; проверка аргументов инструментов
инвариантами домена; `/memory`, `/profile`, `/invariants`, `Цель:` в статус-баре.

**Приёмка.** На каждый базовый и доменный инвариант — положительный и отрицательный тест; попытка
записать ключ подписи в репозиторий отклоняется до вызова инструмента; попытка обновить состав
целей SDK отклоняется; `/clear` не трогает память и профиль.

**Демонстрация.** Отказ по инварианту, обновление памяти по реплике «в этом проекте только qmake».

## P9. Планировщик здоровья репозитория (П)

**Объём.** Перенос расписания и фонового исполнителя; задания: ночная сборка цели, валидация
пакета, обновление индекса, поиск Qt 6-идиом и модулей вне публичного API; объявление о новых
прогонах после ответа, сводка по `/schedule`.

**Приёмка.** `--once` выполняет просроченное задание между двумя вопросами; объявление печатается
один раз; накопленные данные переживают перезапуск; строки не попадают в историю.

**Демонстрация.** Ночная сборка, отчёт по упавшей цели и найденным нарушениям зависимостей.

## P10. Локальная LLM и локальные embeddings (П)

**Объём.** Перенос `llama_server` с пресетами под код; локальная embedding-модель как режим по
умолчанию для индекса; режим «локальная модель + локальный индекс» без облачного ключа и сети;
метрика ток/сек.

**Приёмка.** Вопрос по коду и вопрос по документации портала (при доступной сети) отвечаются
локальной моделью без ключа; смена модели не ломает поиск (векторы разделены по модели);
облачные модели остаются доступны.

**Демонстрация.** Один вопрос на облачной и на локальной модели, сравнение времени, токенов
и качества ответа по коду.

## P11. Тонкий web-фронтенд (M)

**Объём.** `web/`: FastAPI, SSE-поток событий фасада, статика без сборщика (vanilla JS, подсветка
и диффы — vendored), эндпоинты `ask`, `command`, `reports/{kind}`, подтверждение записи и операций
конвейера; флаг `--web [--port]`; TUI и web в одном процессе над одной сессией.

**Приёмка.** В браузере видны ответ с цитатами (`path:L…` и пути документов портала), диффы
патчей и панель задачи; фазы идут потоком; применение патча и установка на устройство ждут
подтверждения; e2e-слой TUI остаётся зелёным.

**Демонстрация.** Тот же сценарий, что в P6/P7, в браузере.

## P12. Паритет и полировка (П)

**Объём.** Сверка `README.md` и `CLAUDE.md` с фактическим поведением (перепроверка списков),
заполнение `## Purpose` у новых возможностей, чистка временных скриптов, полный `pytest`,
`openspec validate --all --strict`.

**Приёмка.** Полный прогон зелёный; документация не обещает того, чего нет; мусора от демонстраций
в репозитории не осталось.

## Расширение области применимости

Расширение не переписывает план: добавляется **пакет домена** (`docs/domains.md` §5) и фаза
на стороне ядра, только если пакету не хватило измерения. Ожидаемые сценарии расширения:

| Что добавляется | Работа |
|---|---|
| Вторая платформа (например Flutter под Аврору) | новый пакет `aurora-flutter`, свои корпуса и проверки; ядро не меняется |
| Вторая версия платформы (Qt 6, если платформа перейдёт) | новый пакет `aurora-qt6`; старый остаётся для поддержки существующих проектов |
| Новый корпус знаний | запись в `corpus.yaml` (локальный каталог или ещё один MCP-сервер документации) |
| Новый инструмент сборки | запись в `tools.yaml` пакета, а не правка `repo_run` |
| Ещё одна проверка | запись в `validation.yaml` пакета |

## Риски и как закрываются

| Риск | Ответ |
|---|---|
| Аврора закрытая и версионируемая: догадка по Qt/Sailfish правдоподобна, но неверна | платформенные факты — только из документации портала со ссылкой и версией (P4, инвариант 10) |
| Сервер документации недоступен (в том числе из-за сетевых ограничений) | честное «документация недоступна» без ответа по памяти; прямой GET отдаёт 403 — проверка вызовом инструмента, отдельный `network`-тест |
| Remote-транспорт MCP не поддержан клиентом донора | отдельная задача P3: ветка streamable HTTP рядом со stdio, транспорт — поле данных, тесты через fake-сервер |
| Сборка и подпись требуют SDK, цели и ключей, которых может не быть | конвейер печатает, чего не хватает, и не подменяет инструмент; коды выхода различают «нет SDK», «нужны данные», «ошибка шага» |
| Установленный SDK старше документации (проверено: SDK 5.1.5 при docs 5.2.1) | версия документа и версия SDK сравниваются и называются в ответе; при рассинхроне ищется раздел нужной версии, а недоступный шаг честно помечается недоступным |
| Устройство недоступно, ключ хоста сменился | причина и совет по конкретной ошибке `ssh`; установка не выполняется молча |
| Установка на устройство и подпись — необратимые операции | подтверждение перед каждым шагом, проверка подписи по строкам вывода `dump`, запрет maintenance-команд до выполнения |
| `rpm -q` вводит в заблуждение для APM-приложений | ловушка описана в промпте домена, проверка — через `ru.omp.APM.GetPackage` |
| Правка `.gitignore` чужого проекта | состояние инструмента — в `.aurora/` через `.git/info/exclude` (прецедент конвейера) и базовый инвариант 3 |
| Опасность расширения области до «отвечаю на что угодно» | домен — единственный источник роли и правил; тест-инвариант «в ядре нет идентификаторов домена» |
