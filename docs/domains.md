# Домены ff.ai: область применимости как данные

Ассистент не «понимает разработку вообще»: у него всегда есть **активный домен** — пакет данных,
который задаёт, о чём он отвечает, что считает источником истины, какие правила не нарушает
и какие команды ему разрешены. Смена предметной области — это добавление каталога, а не правка
кода. Тот же приём, что в доноре применён к пулу моделей (`AVAILABLE_MODELS`) и реестру серверов
(`MCP_SERVERS`): **данные вместо кода**.

## 1. Что определяет домен

| Слой | Что берётся из пакета | Где это работает |
|---|---|---|
| Тематика | роль, границы темы, текст отказа | системный промпт, гейт отказа |
| Знания | корпуса: каталоги репозитория, локальные документы, MCP-серверы документации, версия документации | RAG: индекс, поиск, цитаты |
| Ограничения | таблица инвариантов (правило, запрещённые стемы, ссылка на источник) | проверка ответа и аргументов инструментов |
| Память | правила маршрутизации реплик по слоям, категории | рабочая и долговременная память |
| Персонализация | разделы профиля и вопросы настройки | профиль пользователя |
| Инструменты | белые списки команд, запрещённые команды, разрешённые git-подкоманды, свои MCP-серверы | `repo_run`, `repo_git`, реестр серверов |
| Проверки | детерминированные правила файлов и зависимостей | валидация задачи и `repo_*`-проверки |
| Приёмка | контрольный набор вопросов и сценариев | демонстрация и регрессия |

## 2. Раскладка пакета

```
domains/<id>/
  domain.yaml          # id, title, версия домена, версия платформы, маркеры автоопределения
  prompts/system.md    # роль и предметные правила (аналог assets/system_prompt.md)
  prompts/refusal.md   # граница тематики и фиксированный текст отказа
  invariants.yaml      # таблица правил: номер, правило, запрещённые стемы, источник
  memory_rules.yaml    # образцы → (слой, категория, ключ)
  profile.yaml         # разделы профиля: метка, вопрос настройки
  tools.yaml           # repo_run: белый список; запрещённые команды; git: разрешённые подкоманды
  corpus.yaml          # источники знаний: локальные пути, MCP-серверы, версия документации
  validation.yaml      # детерминированные проверки (файлы, зависимости, запрещённые модули)
  scenarios.md         # контрольные вопросы и ожидания
```

Пакет читается один раз при старте, проверяется по схеме и отдаётся остальному коду **снимком**
(как `context_report()`); агент не ходит в файлы домена напрямую. Ошибка схемы — ошибка старта
с указанием файла и поля, а не молчаливое «домен без инвариантов».

## 3. Выбор домена

Приоритет: аргумент `--domain <id>` → переменная `FFAI_DOMAIN` → **автоопределение по маркерам
репозитория** → домен по умолчанию.

Автоопределение — маленькая таблица правил (как `memory_layers.RULES`), а не эвристика в коде:

| Домен | Маркеры в целевом репозитории |
|---|---|
| `aurora-qt5` | `*.spec` с `%{_datadir}`; `*.pro` с `QT +=`; каталог `qml/`; `CMakeLists.txt` с `Qt5` |

Распознано несколько доменов — берётся наиболее специфичный, выбор печатается в статусе;
распознано ноль — домен по умолчанию, о выборе сообщается строкой журнала. `/domain` показывает
активный домен, версии платформы и найденные маркеры, `/domain switch <id>` переключает вручную;
переключение не переписывает историю, но контекст и корпуса пересобираются.

## 4. Что остаётся доменно-независимым

Ядро не знает ни одного слова из пакета: ни «Аврора», ни «Qt», ни имён инструментов. Проверяется
тестом — как в доноре («ни одного имени инструмента сервера в `core/` и `ui/`»):

- агент, стратегии контекста, сжатие, история, расход, память-механизм, профиль-механизм, инвариант-проверка;
- фасад сессии и события, все панели и редуторы, клавиатура;
- MCP-клиент и реестр серверов, поиск и ранжирование, механика цитат, конвейер задач и инструментов;
- правила безопасности путей и команд (сами списки — из пакета).

Тест-инвариант расширяется: **в `core/` и `ui/` не встречается ни одного идентификатора из
`domains/*/`** (имена команд, модулей платформы, путей документации).

## 5. Расширение домена: чек-лист

1. Создать `domains/<id>/` по раскладке из §2 — данные, без Python.
2. Заполнить `domain.yaml`: версии платформы и документации, маркеры автоопределения.
3. Написать `prompts/system.md` и `prompts/refusal.md`; проверить, что отказ не содержит ответа
   по существу (сценарий в спеке `question-answering`).
4. Собрать `invariants.yaml`: по одному правилу на строку, у каждого — источник (ссылка на
   документацию домена или на решение проекта) и, где возможно, запрещённые стемы для
   машинной проверки. На каждое правило — тест «положительный/отрицательный».
5. Описать корпуса в `corpus.yaml`: локальные каталоги, MCP-серверы документации и **версию
   документации**; для MCP-сервера указать транспорт, команду или адрес.
6. Перечислить проверки в `validation.yaml` и команды в `tools.yaml` (белые списки, а не чёрные).
7. Собрать `scenarios.md` — 8–10 контрольных вопросов и по одному сценарию на каждый инвариант.
8. Прогнать `pytest -q`, затем демонстрацию по `scenarios.md`; расхождения — в задачи, не в промпт.

Новый домен не требует правок в `core/` и `ui/`: если для его поддержки понадобился код —
значит, в механизме доменов не хватает измерения, и это отдельное изменение ядра.

## 6. Совместимость и версионирование

- Пакет объявляет версию платформы (`platform: "Qt 5.6 / ОС Аврора 5.2"`) и версию документации
  (`docs_version: "5.2.1"`). Ответ по платформенным фактам обязан называть версию, для которой он
  проверен: у портала версии документов различаются (`get_doc_versions`), и факт из 4.0.1 может
  быть неверен для 5.2.
- Расширение области (например, добавление Flutter-разработки под Аврору) оформляется **новым
  пакетом**, а не правкой существующего: `aurora-qt5` и `aurora-flutter` — разные наборы правил
  и корпусов. Общие части выносятся в `domains/_shared/` (только файлы, подключаемые по ссылке).
- Схема пакета версионируется полем `schema: 1`; загрузчик отвергает неизвестную схему с явной
  ошибкой, чтобы старый пакет не читался частично.
