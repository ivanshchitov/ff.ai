# ff.ai

Агент-ассистент по разработке приложений под **ОС Аврора на Qt 5.6**: отвечает на вопросы
о кодовой базе и о платформе, ведёт диалог между запусками, помнит контекст по выбранной
стратегии. Основной интерфейс — консольный (TUI).

```bash
git clone <URL репозитория> /path/to/ff.ai && cd /path/to/ff.ai
python3 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
cd /path/to/aurora-project            # целевой репозиторий под ОС Аврора
/path/to/ff.ai/ff-ai.py               # точка входа сама перезапустится в .venv
```

Нужен ключ облачной модели: `echo "OPENCODE_API_KEY=sk-…" > /path/to/ff.ai/.env` — или введите
его в приложении при первом вопросе.

## Что уже работает

| Возможность | Как проверить |
|---|---|
| Вопрос по репозиторию и по платформе | задайте вопрос: ответ придёт с метриками запроса (`⏱ время, токены, стоимость, ток/сек`) |
| Отказ вне области применимости | спросите не про разработку: промпт домена требует фиксированного отказа с объяснением |
| Четыре стратегии контекста | `/settings` → «Стратегия контекста»: резюме, окно, факты, ветки |
| История между запусками | `/exit`, запустите снова — контекст подхватится, экран сообщит, сколько обменов восстановлено |
| Домен как данные | `/domain` покажет пакет, версии платформы и документации, найденные маркеры |
| Отчёты без обращений к модели | `/usage`, `/context`, `/domain`, `/commands` |
| Форматы ответа | `/settings` → «Формат ответа»: свободный, компактный, json, дифф |
| MCP-подключения | строка сводки при старте, `/mcp` — серверы, протоколы и инструменты, `/mcp refresh` — обойти реестр заново |
| Ответ по документации портала | поиск по документации перед вопросом, фрагменты в запросе, `📚 Источники` после ответа; ответ без ссылки на доставленный фрагмент повторяется и заменяется |
| Управление корпусом | `/rag-docs` — отчёт о поиске, `/rag-docs mode on|off`, `/rag-docs version <версия>`, `/rag-docs trace` |
| Отбор кандидатов | вторая ступень: кандидаты оценивает модель, до запроса доходят только прошедшие порог; `/rag-docs retrieval baseline\|enhanced`, `/rag-docs threshold <0..1>` |
| Инструменты репозитория | `/tool` — перечень инструментов с параметрами, `/tool call repo_search query=…` — ручной вызов |
| Корпус кода | индекс исходников целевого репозитория: `/rag-code index [fixed\|structural]`, `/rag-code status`, `/rag-code compare`; лежит в кэше состояния, в репозиторий не пишется |
| Планировщик | `/schedule` — задания, прогоны и накопленное; задания ставит модель или `/tool call`, выполняет `ff-ai-scheduler.py` (в том числе `--once`) |
| Локальная модель | пресеты из `llama_server/models.ini`: `/models` показывает их после облачных; вопрос отвечается без облачного ключа, сервер поднимает и убирает приложение; автозапуск выключается `FFAI_LLAMA_AUTOSTART=0` |
| Web-режим | `--web [--web-host/--web-port]`: тот же фасад в браузере чат-формой — лента вопросов и ответов с композером внизу (Enter отправляет, Shift+Enter переносит строку), фазы и строки журнала под своим ответом, метрики и источники там же, боковая панель с отчётами, задачей, настройками и выбором модели, подтверждения карточкой в ленте |
| Строка состояния | печатается постоянно: модель, домен, имя проекта и активная ветка git, затем задача и цель, если они есть; формата, стратегии и объёма ответа в ней нет |
| Память и профиль | `/memory` (слои, цель, запомнить и забыть), `/profile` (настройка, выбор, удаление): реплики раскладываются по слоям правилами домена, профиль и цель видны в статус-баре |
| Правила домена | `/invariants`: таблица правил и результат последней проверки; правила идут в каждый запрос, нарушение стоит повтора и замены ответа |
| Конвейер операций | `/ops` — состояние SDK и цели, `/ops target <архитектура>`, `/ops build\|sign\|verify\|install\|run`: сборка в `build_<arch>/`, подпись кодовой фразой из окружения, проверка подписи по строкам, установка и запуск с подтверждением |
| Задача с проверкой | `/task add <цель>`, `/task run`, `/task stage <этап>`, `/task stop`: план, патчи файлов с подтверждением, детерминированные проверки домена и отчёт `tasks/<номер>-<слог>.md`; пауза — `p` или Ctrl+C |
| Автовызов инструментов | модель сама выбирает инструменты: один запрос выбора на раунд, цепочка шагов с передачей данных по ссылке `$N`, раунды продолжения при `more`, маршрутизация шага по серверам; `/tool auto on\|off`, `/tool flow` — отчёт о флоу |
| Поиск по коду | первый этап — близость векторов локальной embedding-модели, если векторы для неё есть в индексе; иначе совпадение токенов с названной причиной в `/rag-code trace`; `/rag-code index` после смены модели |
| Ответ по исходникам | поиск по индексу перед вопросом: в запрос уходят фрагменты с путём и строками, ответ обязан назвать файл и привести дословную цитату; `/rag-code retrieval baseline\|enhanced`, `/rag-code threshold <0..1>`, `/rag-code tune before=<n> after=<n>`, `/rag-code mode on\|off`, `/rag-code trace` |

Команды: `/commands`, `/settings`, `/models`, `/clear`, `/usage`, `/context`, `/branches`,
`/domain`, `/rag-docs`, `/rag-code`, `/mcp`, `/tool`, `/task`, `/ops`, `/memory`, `/profile`,
`/invariants`, `/schedule`, `/exit` (автодополнение по Tab).

Флаги: `--repo <путь>` (по умолчанию текущий каталог), `--domain <id>`,
`--web [--web-host/--web-port]`, `--version`.

## Домен и область применимости

Область задаётся **пакетом домена** — данными, а не кодом
([`docs/domains.md`](docs/domains.md)). Первый пакет — `domains/aurora-qt5/`:
роль и границы тематики (`prompts/`), десять инвариантов (`invariants.json`), версии платформы
и документации, маркеры автоопределения (`domain.json`), контрольные сценарии (`scenarios.md`).

Уровни области: целевой репозиторий → платформа (ОС Аврора, Qt 5.6, публичные API, RPM, SDK) →
смежное (общий C++/Qt 5, сборка, отладка) → вне области (отказ). Платформенные факты берутся
из документации портала разработчиков через её MCP-сервер, а не из памяти модели: подключение
и правила запросов — [`docs/domain-aurora-qt5.md`](docs/domain-aurora-qt5.md).

## Структура

```
ff-ai.py            # точка входа: --repo, --domain, --version, перезапуск в .venv
core/               # агент и вся логика без терминала
  config.py           пути состояния (FFAI_*, XDG), модели, цены, границы настроек
  mcp_registry.py     реестр MCP-серверов: записи как данные, серверы домена и свой
  mcp_client.py       подключение по stdio или по адресу, список инструментов, вызов
  docs_retrieval.py   поиск по документации портала: версия, разделы, фрагменты, снимок
  citations.py        проверка ссылок и цитат: идентификатор доставленного фрагмента и цитата
  repo.py             целевой репозиторий: выбор корня и границы файловых операций
  domains.py          загрузка и проверка пакета домена, выбор активного домена
  prompts.py          сборка запроса: роль домена, формат ответа, объём и лимит списка
  agent.py            лог диалога, память стратегии, сжатие, расход сессии
  session.py          фасад для интерфейсов: операции, события, снимки-отчёты
  api_client.py       облачный клиент: повторы, метрики, оценка стоимости
  context_strategies.py, context_compressor.py, history_manager.py, usage.py, answer_settings.py
mcp_server/         # собственный сервер репозитория: отдельный процесс по stdio
ui/                 # терминальный интерфейс: tui_app, экраны-редьюсеры, чтение клавиш
domains/aurora-qt5/ # пакет домена: роль, отказ, инварианты, версии, маркеры, серверы,
                    #   белые списки инструментов, корпус документации, сценарии
assets/             # доменно-нейтральные инструкции: форматы ответа, сжатие, факты
tests/{unit,e2e}/   # pytest: логика без терминала и приложение целиком в псевдотерминале
docs/, openspec/    # документация и спецификации
```

Состояние проекта (история, память, задача, расписание, отчёты задачи и выгрузки) лежит в
`$XDG_DATA_HOME/ff-ai/projects/<хеш пути проекта>` — у каждого проекта своё поддерево
(`core/config.py::project_paths`), поэтому состояние одного проекта не показывается в другом;
профиль пользователя общий: он описывает человека, а не проект. Индекс — в кэше по тому же хешу
(`$XDG_CACHE_HOME/ff-ai`). Запрошенные изменения проекта проходят через подтверждаемый
шлюз патчей; служебные данные, отчёты и снимки остаются снаружи.

## Тесты

```bash
.venv/bin/python -m pytest -q                 # всё: юниты + сквозной прогон в псевдотерминале
.venv/bin/python -m pytest tests/unit -q      # быстрый слой: логика без терминала
.venv/bin/python -m pytest tests/e2e -q       # приложение целиком против stub-сервера
.venv/bin/python -m pytest -s --show-tui=live tests/e2e/…   # видеть экран приложения
```

Сквозные тесты запускают настоящее приложение в псевдотерминале и проверяют отрисованный экран
и содержимое запросов к API; сетевые обращения помечены маркером `network` и по умолчанию
не выполняются.

## Разработка

Работа идёт по OpenSpec: одно изменение = одна фаза плана; сначала спецификация и сценарии,
затем тесты, затем код. Полный `pytest` прогоняется один раз в конце фазы и **до** архивации
изменения. Правила и известные грабли — в [`AGENTS.md`](AGENTS.md).

```bash
openspec validate --all --strict     # проверка спецификаций
openspec archive <change-id> --yes   # перенести дельты в основные спецификации
```

План выполнен целиком: фазы P0–P12 (включая P4.5 и P10.5) закрыты и описаны в
[`docs/roadmap.md`](docs/roadmap.md) — от каркаса, корпусов кода и документации с проверяемыми
цитатами до задачи со сборкой и установкой, памяти и инвариантов домена, планировщика, локальной
модели и тонкого web-фронтенда.

Локальный `/rag-code` ищет по исходникам и Markdown (README, docs) с путями и строками.
Русские термины сохраняются при поиске; JSON/YAML API-описания остаются в корпусе.
IDE-файлы, `.env*`, каталоги состояния, журналы и видео исключены правилами домена.
Портальный корпус `/rag-docs` работает отдельно.

`/help` отвечает о структуре целевого проекта; `/help <вопрос>` — о конкретном
компоненте или соглашении. Сначала соберите локальный корпус: `/rag-code index`.
Команда использует README, docs и исходники через RAG, а свежую git-ветку получает
через собственный MCP `repo_git` (`status --short --branch`). Ответ, источники
и метрики доступны в TUI и web. Этот вход всегда отвечает без запуска задачи
изменения проекта. Для одного запроса включается локальный поиск и отключаются
портальный поиск и автоматический выбор инструментов; прежние настройки затем
восстанавливаются. Отсутствие индекса, устаревшие источники и сбой MCP показываются
явно. Пример демонстрации: [`docs/day31-project-help.md`](docs/day31-project-help.md).

Патчи задач применяются только после подтверждения показанного diff. Перед записью
проверяются актуальные файлы и правила домена; staged-состояние Git сохраняется.
Приватный журнал и снимки находятся вне проекта (`FFAI_CHANGES_DIR`); при перезапуске
незавершённая запись восстанавливается по журналу, неизвестные правки не перезаписываются.
Standalone-конвейеру также нужен callback подтверждения.

`/changes` показывает операции агента; `/changes show <id>` — diff и состояние;
`/changes undo <id>` — обратный diff с подтверждением. Откат сохраняет staged-изменения
и ручные правки до операции. Новые правки затронутых файлов блокируют откат; зависимые
операции отменяются в обратном порядке. После отмены задача на паузе до `/task run`.

Перед планом и каждым патчем агент собирает ограниченный контекст поиска и читает текущие
файлы, включая соглашения проекта. Проверка получает операции задачи и результаты команд.
После apply/undo индекс помечается stale до успешной `/rag-code index`; старые фрагменты
не передаются модели. Контекст задачи продолжает работать через чтение файлов. Автоматический
флоу допускает только инструменты с явным MCP `read_only_hint=true`; ручной `/tool call`
и объявленные проверки сборки сохраняют свой отдельный путь.

Обычная реплика в TUI и web проходит смысловую классификацию: вопрос/исследование
отвечаются без записи, просьба изменить код или документы запускает существующий конвейер
задачи, неоднозначная цель требует уточнения. Классификация учитывается в `/usage`.
«Ничего не меняй» блокирует разработку; даже запрос разработки не подтверждает diff.
Занятая сессия возвращает busy. `/task` остаётся явным входом без классификации.
Web принимает необязательный `request_id`: повтор возвращает сохранённую задачу без
повторного запуска, включая завершённую задачу и перезапуск приложения.

Идентификатор операции виден до подтверждения и в отчёте задачи. Web связывает diff,
результаты проверок, stale-индекс и отмену с сообщением задачи; после `/changes undo`
панель обновляется сразу. В TUI показывается полный diff.
Повтор `request_id` после `/task stop` также не запускает задачу заново; новая цель
требует нового идентификатора. Сбой между применением и сохранением задачи восстанавливает
связь операции с подзадачей по журналу. Для старых сохранений новые поля необязательны.

Перенесённые навыки: `.agents/skills/feature-builder` и
`.agents/skills/solve-challenge-task` (ссылки для Claude Code, OpenCode и oh-my-pi).
Демонстрации используют отдельные каталоги `FFAI_*` и временную копию проекта.
Подготовка к дням 31–35 описана в
[`плане реализации`](docs/superpowers/plans/2026-10-11-development-agent-preparation.md).

AI-ревью PR запускается отдельно от TUI/web:

```bash
.venv/bin/python ff-ai-review.py --repo /path/to/aurora-project --domain aurora-qt5 \
  --base main --head HEAD --output /path/to/review-results
```

Конвейер читает diff и файлы выбранного коммита, ищет контекст отдельно в коде и
Markdown-документации и сохраняет `review.md` и `report.json` со стадиями, источниками
и расходом модели. Каталог результатов — пустой и вне проекта. Рабочее дерево,
git-index и история диалога сохраняются. Workflow для PR, настройка ключа и
демонстрация на WebDavClient описаны в [инструкции дня 32](docs/day32-pr-review.md).
В GitHub успешное ревью публикуется в один обновляемый комментарий PR.
Потенциальные баги и архитектурные проблемы блокируют обязательную проверку
`AI review gate`; рекомендации без таких проблем не блокируют merge.
