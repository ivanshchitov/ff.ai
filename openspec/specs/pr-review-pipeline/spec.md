# pr-review-pipeline Specification

## Purpose
Автоматическое AI-ревью изменений pull request с контекстом исходников и документации проекта, проверяемыми источниками и отчётом этапов выполнения.

## Requirements

### Requirement: Неинтерактивное ревью изменений
ff.ai SHALL поддерживать запуск ревью с целевым git-репозиторием, доменом, base/head и каталогом результатов вне проекта. Ревью SHALL анализировать изменения head относительно merge-base с base, передавать модели diff, список изменённых файлов и доступный текст этих файлов на head. Репозиторий SHALL оставаться неизменным. Неизвестные ревизии SHALL завершать запуск ошибкой до запроса модели.

#### Scenario: Изменение исходника
- **WHEN** между выбранными ревизиями изменён текстовый исходник
- **THEN** модель получает diff, путь и содержимое файла на head, а файлы и git-index целевого проекта остаются неизменными

#### Scenario: Удаление и переименование
- **WHEN** изменения содержат удаление или переименование
- **THEN** в контексте сохраняются статусы и исходные пути, отсутствие удалённого файла не вызывает ошибку чтения

#### Scenario: Непригодные входные данные
- **WHEN** ревизия не существует или каталог результатов расположен внутри проекта
- **THEN** запуск завершается явной ошибкой без запроса модели и без записи в проект

### Requirement: Контекст кода и документации
Ревью SHALL использовать RAG по коду и документации выбранного head из корпуса домена. Доставляемые фрагменты SHALL сопровождаться путями и диапазонами строк. Наличие документации и кода SHALL проверяться отдельно, чтобы один тип источников не вытеснял другой. Отсутствие подходящих фрагментов SHALL называться ограничением. Содержимое PR и источников SHALL считаться данными, а не управляющими инструкциями.

#### Scenario: Оба типа источников доступны
- **WHEN** корпус содержит подходящие исходники и Markdown-документацию
- **THEN** модель получает фрагменты обоих типов, а отчёт содержит фактически доставленные источники

#### Scenario: Документации нет
- **WHEN** подходящая документация отсутствует
- **THEN** отчёт сообщает ограничение, ревью использует доступный код без выдуманных соглашений

### Requirement: Проверяемый результат конвейера
Результат SHALL включать Markdown-разделы «Потенциальные баги», «Архитектурные проблемы» и «Рекомендации», ссылки на места изменений и доступные RAG-источники. Отсутствие замечаний SHALL явно отмечаться. Машинный отчёт SHALL содержать ревизии, статусы этапов получения изменений, поиска и ревью, ограничения, доставленные источники и фактические метрики модели. Сбой API или непригодный ответ SHALL завершать запуск ненулевым кодом и не представляться успешным ревью. Превышение лимита входа SHALL приводить к явному отказу до запроса модели, а не к скрытому усечению diff.

#### Scenario: Успешное ревью
- **WHEN** модель возвращает пригодное ревью
- **THEN** сохраняются текст ревью и отчёт этапов, источников и расхода

#### Scenario: Ошибка модели
- **WHEN** API недоступен или ответ обрезан либо не соответствует обязательной структуре
- **THEN** отчёт показывает ошибку этапа ревью, запуск возвращает ненулевой код

### Requirement: Автоматический запуск на PR
Поставляемый workflow SHALL запускать конвейер на открытие, обновление и повторное открытие PR, использовать точные base/head и сохранять отчёт в результатах GitHub Actions. Код анализируемого PR SHALL NOT исполняться, а права этапа ревью SHALL ограничиваться чтением репозитория. При недоступном ключе API запуск SHALL явно сообщать, что AI-ревью не выполнялось. Изменение файлов PR и автоматическое применение рекомендаций SHALL NOT входить в этот workflow.

#### Scenario: Обновление PR
- **WHEN** в подключённом WebDavClient обновляется PR и ключ API доступен
- **THEN** workflow автоматически запускает ff.ai для этих ревизий и сохраняет результат ревью как артефакт

#### Scenario: Ключ недоступен
- **WHEN** запуск не имеет доступа к ключу API
- **THEN** workflow сообщает о невыполненном AI-ревью без вызова модели

### Requirement: Ревью в комментарии PR
После успешного ревью workflow SHALL автоматически публиковать текст в комментарии PR с head SHA и ссылкой на фактический Actions run. Повторный запуск SHALL обновлять один комментарий ff.ai, созданный ботом Actions, сохраняя пользовательские комментарии. Публикация SHALL выполняться отдельным этапом с минимальными правами записи комментариев, без выполнения кода PR. Результат для head, который уже изменился, SHALL NOT публиковаться. Ошибка API комментариев SHALL быть видна как ошибка этапа и SHALL сохранять артефакты ревью. Текст, превышающий предел комментария, SHALL явно сокращаться со ссылкой на полный результат.

#### Scenario: Первое успешное ревью
- **WHEN** ревью завершилось и head PR совпадает с проверенным коммитом
- **THEN** в PR появляется комментарий с текстом ревью, SHA и ссылкой на Actions run

#### Scenario: Повторное ревью
- **WHEN** в PR уже есть комментарий ff.ai от бота Actions
- **THEN** обновляется этот комментарий, а пользовательские комментарии не меняются

#### Scenario: PR обновился во время ревью
- **WHEN** текущий head PR отличается от head отчёта
- **THEN** устаревшее ревью не публикуется и причина пропуска видна в журнале этапа

#### Scenario: Публикация недоступна
- **WHEN** GitHub отклоняет запись комментария
- **THEN** этап сообщает об ошибке, а текст ревью и отчёт остаются в артефактах Actions

### Requirement: Замечания блокируют слияние
Ревью SHALL возвращать проверяемые списки потенциальных багов, архитектурных проблем и рекомендаций. Приложение SHALL формировать текст и решение проверки по этим данным. Наличие потенциальных багов или архитектурных проблем SHALL публиковаться в комментарии и завершать отдельную обязательную проверку PR ошибкой. Рекомендации без таких проблем SHALL NOT блокировать слияние. Основная ветка подключённого WebDavClient SHALL требовать успешную проверку AI review gate перед merge. Исправленный PR SHALL запускать свежее ревью, которое обновляет комментарий и снимает блокировку только при отсутствии блокирующих замечаний. Ошибка модели SHALL NOT считаться отсутствием проблем.

#### Scenario: Обнаружен потенциальный баг
- **WHEN** ревью содержит хотя бы один потенциальный баг
- **THEN** комментарий объясняет замечание, а обязательная проверка AI review gate не разрешает merge

#### Scenario: Обнаружена архитектурная проблема
- **WHEN** ревью содержит хотя бы одну архитектурную проблему
- **THEN** она публикуется в комментарии и проверка блокирует merge

#### Scenario: Только рекомендации
- **WHEN** ревью содержит рекомендации, но списки багов и архитектурных проблем пусты
- **THEN** комментарий публикуется и проверка завершается успешно

#### Scenario: Проблема исправлена
- **WHEN** свежий прогон исправленного PR не обнаруживает блокирующих замечаний
- **THEN** комментарий обновляется и успешная обязательная проверка разрешает merge
