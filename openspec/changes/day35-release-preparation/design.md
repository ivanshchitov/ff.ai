## Context

Мотивация и согласованная граница описаны в `proposal.md`. Контракт — `specs/release-preparation/spec.md`. Исходная задача — `../ai-advent-challenge-9/week7/day35/README.md`: реальное AI-приложение или пайплайн под конкретную задачу, сдача «Видео + Код». Пример — `../WebDavClient`.

В ff.ai уже есть:

- `core/pr_review.py`: безопасное чтение Git, снимок текстового корпуса, RAG исходников и документов, скрытие секретов, строгий результат ревью. Его `collect_changes` использует merge-base; этот контракт сохраняется.
- `core/aurora_ops.py`: исполнитель доменных команд и сборки с внедряемым раннером. `state_path` зависит от корня переданного проекта; создавать экземпляр на исходном WebDavClient для подготовки релиза нельзя.
- `core/domain_checks.py`: проверки патча. Проверка добавленных строк diff не является полной проверкой файлов релизного снимка.
- `core/session.py`: сериализация команд, события фаз и журнала, API-клиент и учёт расхода.
- `config.project_paths(root)["exports_dir"]`: изолированный по проекту каталог отчётов с существующим переопределением FFAI_EXPORTS_DIR.

Дерево ff.ai и пример WebDavClient были чистыми при исследовании. Последний существующий тег ff.ai — v0.34; следующий предлагаемый выпуск — v0.35, только после завершения работ и отдельного разрешения тега.

## Goals / Non-Goals

**Goals:**

- Связать точный диапазон Git, проверки и два ограниченных AI-запроса единым сериализованным запуском.
- Разделить доказательства выполнения, модельные замечания и ограничения проверки в одном пакете.
- Подготовить демонстрацию в настоящем TUI с живой моделью и фактическим результатом сборки.

**Non-Goals:**

В дополнение к `proposal.md`: произвольные пользовательские shell-команды, автоматическое исправление замечаний, параллельные модельные исполнители, автоматическое возобновление после прерывания и отдельная веб-панель релизов не добавляются. Web использует существующую отправку команд и события.

## Decisions

### 1. Один конвейер и существующий фасад

Новый `core/release_preparation.py` отвечает за вход, последовательность этапов, итог и сохранение. Фасад разбирает `/release prepare --base <ref> --head HEAD [--arch <architecture>]` и `/release status`, передаёт зависимости и публикует события. Голый `/release` равен status. Base обязателен, head допускает любой ref, разрешающийся в текущий HEAD; архитектура берётся из явного параметра или значения домена по умолчанию.

Конвейер получает интерфейсы чтения репозитория, проверки/сборки и модельного запроса; это позволяет проверить сбои без SDK и сети. UI не читает внутренности конвейера. Отдельный процесс CLI в первой версии не нужен; скрипт демо вызывает тот же фасад. Альтернатива — независимый релизный агент с собственным циклом — дублировала бы управление и расход.

### 2. Прямой диапазон и неизменяемый вход

Проверить чистоту `git status --porcelain` с неигнорируемыми untracked, разрешить ref через `rev-parse --verify --end-of-options <ref>^{commit}`, проверить base-предка и текущий HEAD. Полные SHA становятся единственными ревизиями следующих чтений. Читать diff base → head с запретом external diff/textconv и без shell.

Повторно использовать безопасное Git-чтение из PR-ревью; при необходимости вынести общий узкий помощник с сохранением его прежних тестов. Не менять `collect_changes` PR-ревью на прямой diff. Для релиза даже при разошедшихся ветках нельзя молча менять base на merge-base. До итогового статуса повторно сверить исходный HEAD и чистоту дерева.

Изменённые файлы получать по NUL-разделённым записям с учётом удаления и переименования. Для удалённого фрагмента источником является base, для актуального файла — head. Лимиты числа файлов, размера diff и переданного контекста первоначально взять из существующего PR-ревью; превышение — явный отказ, без тихой обрезки diff.

### 3. Разные снимки для анализа и сборки

Текстовый снимок для RAG использует правила корпуса домена и существующее скрытие секретов. Источники получают непротиворечивые идентификаторы с SHA, путём и диапазоном строк; модель ссылается только на переданный набор. Diff также оформляется как источник с явно указанной ревизией.

Сборочный снимок материализуется из обычных Git blob выбранного head в приватный каталог запуска. В него не копируются исходная `.git`, hooks, пользовательское окружение, `.env` и ключи. Пути и размеры проверяются до записи; симлинки и подмодули не разыменовываются, пропуски называются в отчёте. Ограничение размера отдельной сборочной копии — 256 MiB суммарно и 32 MiB на обычный файл; превышение делает сборку unavailable с причиной. Двоичные отслеживаемые ресурсы в этих пределах копируются побайтно.

Нельзя собирать очищенный RAG-снимок: редактирование литералов меняет программу, а корпус исключает ресурсы. В сборочную копию содержимое обычных файлов переносится без преобразования; модель и сохраняемые журналы получают только очищенные данные. Секреты, необходимые для реального запуска приложения, не выдумываются и не вставляются. Если копии недостаточно для сборки, результат явно ограничен.

Экземпляр существующего исполнителя операций получает корень сборочной копии, где остаются служебное состояние и `build_<arch>/`. Доступные цели читаются у инструмента. Политика окружения и таймауты наследуют ограничения действующего исполнителя; новых произвольных команд нет. Сборка выполняет код доверенного локального проекта, поэтому этот сценарий не подключается к PR из внешних fork и не меняет read-only CI-ревью дня 32.

### 4. Правила релизных проверок — данные домена

Добавить необязательный `release.json` в пакет домена и соответствующую загрузку/валидацию в `core/domains.py`. Он объявляет шаблоны файлов метаданных, обязательные элементы и обязательность проверок, а не имена проекта или абсолютные пути. В пакете разработки обязательны метаданные пакета и сборка; тесты проекта необязательны и изначально not_configured. У домена без release-конфигурации prepare возвращает понятный отказ до модели и сборки.

Живой прогон уточнил настройки адаптера: необязательные target_pattern и build_command в release.json переопределяют только экземпляр операций релизного запуска. Основная цель выбирается без снимков; команда теневой сборки получает путь к исходникам и no-pull-build-requires, сохраняя состав установленных зависимостей. Одну команду ограничиваем 180 секундами с сохранением частичного вывода. Прежний `/ops` не меняется. Обоснование синтаксиса — MCP-документ портала [sfdk, версия 5.1.5](https://developer.auroraos.ru/doc/5.1.5/sdk/app_development/build/build_engine/sfdk) и локальная справка установленного SDK 5.1.5.105-mb2.

Проверять полные актуальные файлы снимка, включая согласованность идентификатора приложения в объявленных метаданных. Платформенные расширения, поля, запрещённые конструкции и команды живут только в пакете домена. Использовать существующие проверки там, где их контракт подходит; не считать проверку добавленных строк полной проверкой проекта. Правила не объявляются полным аудитом соответствия требованиям магазина.

Настроенная проверка тестов использует только явно объявленный в домене допустимый инструмент; при отсутствии настройки никаких сгенерированных моделью команд не запускается. В отчёте указывается, что not_configured не доказывает отсутствие ошибок. Подпись и устройство не являются проверками этой версии.

### 5. Два модельных запроса по цепочке

Ревьюер получает цель подготовки, точный diff, относящиеся к нему исходники и документацию, фактические статусы проверок. Ответ — строгий JSON `findings`, каждый элемент содержит severity (`blocker` или `recommendation`), текст и непустой список идентификаторов источников. Неизвестные поля, типы, уровни и ссылки отклоняются. Ограничение — 20 замечаний, до 2000 символов текста на замечание.

Автор получает те же доступные источники, результаты проверок и валидированный результат ревьюера. Ответ — строгий JSON `summary` и `items`; каждый пункт содержит текст и непустой список известных источников. Ограничение — до 30 пунктов по 2000 символов и summary до 2000 символов. Markdown генерируется приложением. Автор не может удалить блокер или изменить статус проверки. При отсутствии изменений пользователь получает отказ до модели.

История, профиль, память и результаты других релизов не передаются. Данные файлов не становятся инструкциями. Используются API-клиент сессии, выбранная модель и существующий учёт расхода, без повторного создания клиента и без собственных таблиц цен. Настройки ответа обычного чата не должны обрезать структурированный результат релизного запроса; отдельные технические бюджеты задаются вызовом, не изменяя пользовательские настройки.

Отдельный контекст не требует процессов или параллельных писателей. Невалидный/обрезанный ответ или ошибка API фиксируются без дополнительных скрытых повторов поверх существующих транспортных retry. При сбое ревьюера этап автора отмечается невыполненным. После провала сборки AI всё ещё может подготовить анализ и черновик для разработчика, но итог остаётся blocked.

### 6. Итог вычисляет приложение

Проверка содержит id, required, status, reason и ссылки на свидетельства. AI-этап отдельно содержит status, валидированные данные и метрики. Порядок решения:

1. Любая failed обязательная проверка либо blocker валидированного ревью → blocked.
2. Иначе unavailable/not_configured обязательной проверки, ошибка AI, изменение исходного входа либо прерывание → incomplete.
3. Иначе → ready_for_manual_release с явными ограничениями, включая ненастроенные необязательные тесты.

Сбой подготовки окружения не маскируется под дефект приложения. Вывод failed сборки остаётся failed даже при положительном модельном анализе. Фраза «готов к ручному выпуску» всегда сопровождается границами выполненных проверок.

### 7. Хранение без нового FFAI-пути

Материалы лежат в `config.project_paths(root)["exports_dir"]/releases/<run-id>/`; существующий FFAI_EXPORTS_DIR уже изолируется тестами и демо. Проверять, что разрешённый путь с учётом симлинков расположен вне целевого проекта. Новые переменные окружения не требуются.

`checks.json` с schema=1 содержит run_id, состояние запуска, base/head, домен, архитектуру/цель, этапы, проверки, источники, ограничения, метрики, итог, относительные пути артефактов и SHA-256 полученных пакетов. Запись атомарная через временный файл и replace; исходные секреты в модельные отчёты и логи не попадают. Фактически полученный RPM хранится приватно как сборочный артефакт и не загружается автоматически.

Указатель `releases/latest.json` обновляется атомарно после принятия запуска. При чтении допускается только корректный run-id и каталог внутри releases; произвольные пути из файла не открываются. `/release status` показывает сохранённый результат без модели. Если в файле остался running после перезапуска, отображается incomplete с причиной прерывания; повторный запуск автоматом не начинается. До создания каталога ошибки ввода возвращаются пользователю и не затирают последний результат.

Report.md формируется на каждом завершённом этапе, включая ошибки. Release-notes.md появляется только после успешной генерации и содержит пометку «черновик». При сбое файловой системы фасад называет ошибку сохранения; нельзя обещать сохранение при отсутствии места или доступа.

### 8. Проверка и демонстрация

Юнит-слой проверяет входы, прямой diff, изоляцию, полные метаданные, приоритеты статусов, схемы и источники AI, секреты, сбои, восстановление статуса и учёт расхода. Сборка тестируется внедрённым исполнителем; модель — заглушкой с проверкой переданного контекста. Эти проверки не доказывают качество живого AI и работоспособность SDK.

`scripts/day35_demo.py` работает на изолированной копии WebDavClient и перенаправляет все FFAI-пути существующим способом дня 34. Подготовленная регрессия ограничена понятным изменением пользовательского поведения; отдельная детерминированная ошибка метаданных гарантированно демонстрирует blocked независимо от ответа модели. До/после сверяются исходный WebDavClient и состояние пользовательских файлов; demo не коммитит в оригинале. Создание временной истории сценария разрешается явно через флаг демо, действующий только в его каталоге.

Два прогона: регрессия/ошибка метаданных → blocked; исправленный вариант → ready_for_manual_release только при прошедшей настоящей сборке и успешном AI. Если SDK недоступен, второй итог incomplete, в видео это показывается прямо. После перезапуска проверяется status без нового расхода. Сухой прогон сохраняет SHA, статусы, источники, метрики, проверки оригинала и пути материалов.

Запись настоящего TUI длительностью 30–600 секунд проверяется по ключевым кадрам. Материалы — `videos/day35-demo.mp4`, `videos/day35-README-draft.md`, `videos/day35-release-notes.md`. Ссылки на код строятся только по существующему тегу, URL видео добавляется после загрузки пользователем. README челленджа автоматически не меняется.

## Risks / Trade-offs

- AI может пропустить дефект → статус ограничен проверенными условиями; ручные сценарии перечисляются отдельно, ошибки не объявляются исключёнными.
- Большой проект, симлинки или подмодули не помещаются в безопасную копию → назвать точное ограничение, не собирать неполный снимок как полноценный релиз.
- Литералы OAuth могут попасть в сборочный артефакт → приватное хранение, отсутствие автоматической публикации; распознанные данные скрываются из модели, отчётов и видео.
- Сборка выполняет проектный код → только выбранный локальный проект, отдельная копия, существующие ограничения раннера; это не песочница для недоверенного PR.
- Сбой API оставляет неполный пакет → атомарные промежуточные результаты и incomplete, новый запуск только по явной команде.
- Два модельных запроса увеличивают стоимость → ограниченный контекст и фактические метрики обоих этапов, без автономного цикла исправлений.

## Migration Plan

Изменение аддитивное: новые команды, модуль и необязательная конфигурация домена. Старые состояния и команды сохраняют поведение. Откат кода прекращает новые запуски, ранее созданные Markdown/JSON остаются внешними материалами пользователя и не удаляются. Коммиты, теги и публикация выполняются только после отдельного явного разрешения пользователя; подтверждение идеи не считается разрешением Git-мутаций.
