## Context

Условия: `../ai-advent-challenge-9/week7/day32/README.md`, контекст: `../ai-advent-challenge-9/week7/README.md`. Целевой проект — личный `ivanshchitov/WebDavClient`. Мотивация и границы поведения — proposal и `pr-review-pipeline`.

В ff.ai уже есть APIClient, данные домена, общий корпус Markdown и исходников, CodeRetriever и отчёты расхода. Интерактивная сессия содержит память, историю и конвейер изменений; CI-ревью не нуждается в этом состоянии. Оба репозитория перед началом чистые; ff.ai на main, последний тег v0.31.

## Goals / Non-Goals

**Goals:** самостоятельный неинтерактивный вход в существующее ядро, единый путь локального и CI-ревью, источники и журнал этапов. Закрыть все критерии дня 32 и показать пользу на WebDavClient.

**Non-Goals:** UI-команды ревью, исправление найденных ошибок, публикация комментариев, новый универсальный framework агентов. Неделя описывает субагентов для сложных задач; здесь выбран линейный конвейер, без дополнительных модельных запросов на распределение работы.

## Decisions

1. **CLI и небольшой модуль ядра.** Новый `ff-ai-review.py` принимает `--repo`, `--domain`, `--base`, `--head`, `--output`, выбор модели. Общая логика находится в `core/pr_review.py`, промпт — в assets. Используются существующие загрузчики домена, APIClient и поиск. Альтернатива — запуск полной AssistantSession: лишнее пользовательское состояние и риск классификации ревью как разработки.

2. **Снимок коммита, а не рабочее дерево.** Только read-only git с отключёнными optional locks, external diff и textconv; base/head сначала разрешаются в commit SHA. Diff строится от merge-base. Список файлов читается с NUL-разделителями и статусами; данные head извлекаются из git в приватный временный корпус вне проекта. Не читать файлы через пути из PR без проверки границ; не следовать симлинкам, не запускать hooks, сборку, submodules или скрипты PR. Бинарные файлы и файлы за пределами правил корпуса отмечаются как ограничения. Альтернатива — checkout PR поверх оригинала — меняет пользовательский проект.

3. **Раздельная доставка кода и документов.** Переиспользовать существующее разбиение и baseline-поиск по токенам; обеспечить отдельную квоту для Markdown и для исходников, с запросами на основе путей и изменённых идентификаторов. Индекс создаётся для выбранного head вне проекта. Источники в итоговом отчёте указывают пути исходного проекта, строки и head SHA. Векторный поиск и портал не обязательны для дня 32: документация проекта уже содержит договорённости, необходимые ревью. Вывод не содержит платформенных утверждений без подтверждённого источника.

4. **Один запрос ревью.** Модель получает инструкции домена, строгую структуру ответа и явно обозначенные недоверенные данные: diff, тексты файлов, RAG. Без инструментов записи и исполнения. Лимиты файлов, diff и общего контекста проверяются перед вызовом; слишком большой PR не выдаётся за полностью проверенный. Проверяются обязательные разделы, непустой текст и finish_reason. Метрики берутся из AnswerMeta. Автоматические повторы на содержание ответа не добавляются.

5. **Отчёт как артефакт.** `review.md` и `report.json` сохраняются вне проекта, включая статусы и длительности этапов и ошибки без секретов. Успешный код выхода означает выполненное ревью, а не отсутствие замечаний. Ошибка API или непригодный ответ — ненулевой выход. Нет действий от имени пользователя в комментариях PR.

6. **GitHub Actions в WebDavClient.** Подготовить caller workflow на `pull_request` и переиспользуемый workflow в ff.ai. Исполнитель ff.ai и actions закрепляются на доверенных ревизиях; head PR используется только как данные. Ключ `OPENCODE_API_KEY` берётся из GitHub Secrets, checkout не сохраняет credentials, разрешения — contents: read. У fork PR ключ обычно недоступен: явный статус «не выполнялось»; не обходить ограничение через исполнение PR в `pull_request_target`. Установку caller и настройку секрета выполняют после подготовки проверяемых файлов с учётом разрешений среды. Публикация ff.ai нужна до реального удалённого запуска.

7. **Демо и приёмка.** Локальный запуск на временной копии WebDavClient с контролируемым изменением, создающим очевидную регрессию; показать diff, доставленные код и coding_conventions, три раздела ревью и реальные метрики. Записать экран проверенным рекордером. Локальный прогон не называть выполненным GitHub Action; удалённый запуск подтверждать только фактической ссылкой на run после разрешённой публикации.

## Risks / Trade-offs

- Недостоверные замечания модели → каждое замечание связывается с местом изменения; отчёт является рекомендацией, не решением о merge.
- Секреты в данных проекта → фильтрация запрещённых путей и проверка отправляемого контекста существующими средствами; демо предварительно проверяется без печати значений.
- Недоступность модели или документации → отдельные статусы ошибки и ограничения, без фиктивного успеха.
- Слишком большой PR → явный отказ до API; разбиение на несколько модельных задач оставлено для будущего расширения.
- Последовательный номер релиза и запись недели совпали → предлагаем v0.32 после существующего v0.31; ссылка на тег появляется только после его фактического создания.

## Migration Plan

Новые файлы не меняют существующий интерактивный сценарий. После TDD и полного локального набора архивировать OpenSpec. Подключить workflow к WebDavClient, вручную добавить ключ в GitHub Secrets, опубликовать разрешённый релиз ff.ai и проверить отдельный PR. Откат подключения — удаление caller workflow, без миграции данных пользователя.
