## Context

См. `proposal.md` — Why. Что уже есть: фасад сессии (`core/session.py`) с операциями, событиями
и снимками; домен как данные (`core/domains.py`, пакет `domains/aurora-qt5/`); границы файловых
операций (`core/repo.py`, `ensure_inside`); интерфейс (`ui/tui_app.py`) с командами и панелями.
Что мешает: у ассистента нет ни одного источника данных о репозитории и платформе.

Пакет `mcp` установлен в версии **2.3.0**, и его API отличается от того, что использовал донор:
вместо `ClientSession` + `stdio_client` есть единый `mcp.client.client.Client`, который принимает
и `StdioServerParameters`, и **строку адреса** для remote-транспорта. Проверено живым вызовом:
`Client("https://developer.auroraos.ru/api/mcp")` отдаёт `list_tools()` (8 инструментов портала)
и `call_tool("echo", ...)`; при закрытии сессии сервер отвечает `403` на попытку её завершить —
это его особенность, а не сбой подключения.

## Goals / Non-Goals

**Goals:**

- Один клиент с двумя транспортами и одинаковым жизненным циклом «поднять — спросить — закрыть».
- Реестр как данные: серверы области применимости объявляет пакет домена, собственный сервер —
  ядро; ни одного имени инструмента конкретного сервера в `core/` и `ui/`.
- Собственный сервер репозитория с жёсткими границами: пути внутри корня, команды из белого
  списка, git только на чтение, никакой записи в целевой репозиторий.
- Наблюдаемость: снимок по каждому серверу и ручной вызов инструмента; ноль запросов к модели.

**Non-Goals:**

- Автовызов инструмента моделью, цепочки и раунды — фаза P5 (`mcp_tools`, `/tool auto`).
- Использование документации портала как корпуса ответа с цитатами и правилами версий — фаза P4.
- Запись в целевой репозиторий (патчи) — фаза P6, где есть подтверждение и прогон проверок.
- Долгоживущие соединения: каждое подключение поднимается на время операции и закрывается.

## Decisions

**Клиент остаётся синхронным с `asyncio.run` внутри.** Главный цикл приложения — обычный
`input()`; перевод на асинхронность стоил бы правки всего `ui/` ради двух команд. Донорский приём
сохранён, но внутренность переписана под API 2.3: вместо ручного `ClientSession` + transport-стека
берётся `Client(...)`, который сам выбирает транспорт по типу аргумента. Альтернатива — поддерживать
две ветки кода (свой стек для stdio и для http) — дала бы вдвое больше кода и вдвое больше
способов сломаться на смене версии пакета.

**Транспорт — поле данных, а не отдельный класс.** `MCPServerSpec` объявляет имя, транспорт,
команду с аргументами (stdio) либо адрес (http), описание, ключи окружения и необязательное имя
инструмента проверки. Проверка: сервер объявляет инструмент — клиент вызывает его с пробным
сообщением; не объявляет — успешным считается получение списка инструментов. Имя инструмента
проверки тоже приходит из данных, иначе в ядре появилось бы чужое имя.

**Собственный сервер — read-only по отношению к целевому репозиторию.** Перечень файлов, чтение,
поиск, git-чтение, разрешённые команды сборки и сохранение выгрузки **вне** репозитория. Патч
в этой фазе не пишется сознательно: инвариант «не трогать файлы вне запрошенного изменения»
проверяется кодом только вместе с конвейером задачи, где есть подтверждение. Это делает P3
безопасной фазой: даже ошибочный вызов инструмента не может испортить чужой код.

**Белые списки — из пакета домена.** `tools.json` объявляет разрешённые команды сборки и
git-подкоманды; сервер читает пакет сам (он запускается тем же интерпретатором и видит `core/`).
Дублировать списки в коде сервера нельзя: домен для того и вынесен в данные, чтобы правка
области не требовала правки кода.

**Обход реестра — при старте, последовательно, и соединение не живёт дольше операции.** Сводка
печатается строкой до заголовка; упавший сервер считается и не мешает остальным. Живые соединения
всю сессию означали бы фоновой поток с событийным циклом и корректное завершение при выходе —
для отчёта это лишняя сложность.

**Снимки вместо внутренностей.** `MCPReport` (сервер, версия, протокол, инструменты, ошибка) и
`MCPToolResult` (сервер, инструмент, аргументы, текст, ошибка) — то, что рендерит интерфейс;
он не трогает клиент. Всё, что пришло от чужого процесса, экранируется при печати.

## Risks / Trade-offs

- [Remote-сервер портала недоступен из сети] → `/mcp` печатает причину, сводка считает его
  недоступным, сессия продолжается; `network`-тест отделяет это от обычных тестов.
- [Смена API пакета `mcp`] → транспорт сосредоточен в одном модуле; проверка версии зафиксирована
  нижней границей в `requirements.txt`, а поведение — тестами против локальных fake-серверов.
- [Собственный сервер запускает команды] → белый список из пакета, запуск без оболочки,
  таймаут, ограничение вывода; команда вне списка отклоняется с перечнем допустимых.
- [Сервер читает пакет домена сам] → если пакет сломан, сервер сообщает об этом как `isError`;
  это не роняет приложение, потому что вызов инструмента — отдельный процесс.
- [Инструменты могут вернуть очень много текста] → у каждого инструмента есть ограничение
  объёма и обрезка с пометкой; в P5 к этому добавится бюджет контекста.
- [`403` при завершении сессии портала] → это особенность сервера: подключение уже отработало,
  диагностика не считается ошибкой отчёта.

## Migration Plan

Состояние на диске не меняется, новых файлов состояния нет. Пакет домена дополняется двумя
файлами (`servers.json`, `tools.json`) — они необязательны, и домен без них грузится как прежде,
поэтому расширение области не ломается. Откат — удаление новых модулей и записей реестра.
