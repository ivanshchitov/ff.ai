## Context

См. `proposal.md` — Why. Что уже есть: корпус документации (P4) — поиск по разделам, версия,
кандидаты со сниппетами, выгрузка и вырезка фрагментов, снимок `DocsReport`, проверка ссылок
и цитат. Замеры контрольного прогона P4: из трёх доставленных фрагментов релевантен один; поиск
портала ранжирует словами, а не смыслом вопроса.

## Goals / Non-Goals

**Goals:**

- До модели доходят только кандидаты, признанные релевантными относительно исходного вопроса.
- «Нашлось, но не то» — отдельное состояние с честной инструкцией, а не шум в запросе.
- Отбор наблюдаем: оценки, причины, режим и порог видно в отчёте.

**Non-Goals:**

- Переписывание запроса моделью: поиск по-прежнему идёт исходным вопросом. Оценка кандидатов —
  это про отбор уже найденного, а не про качество поисковой формулировки.
- Жёсткий отказ при слабом отборе: домен разрешает смежные вопросы (уровень 3), поэтому состояние
  «найдено, но не подошло» даёт инструкцию, а не замену ответа.
- Замена порога на «взять top-K»: порог задаёт пользователь, а не модель.

## Decisions

**Оценка — вспомогательный запрос агента, а не работа ретривера.** Ретривер остаётся чистым
относительно HTTP: он получает функцию оценки (`rate`) и вызывает её между поиском и выгрузкой
текстов. Так порядок «сначала отсеять, потом выгружать» соблюдается без разбиения публичного API
на две операции, а расход, фаза и учёт остаются там, где им место — в агенте.

**Порог применяется к оценке, а не к положению в списке.** Модель обязана оценить **все** кандидаты,
включая слабые (это прямо сказано в ассете): приложение само решает, что оставить. Иначе «выбери
лучшие» превратилось бы в выбор наименее неподходящего, что для платформенных фактов опаснее
отсутствия источника.

**Отказ оценки останавливает доставку.** Неполный ответ, чужой идентификатор, оценка вне диапазона,
неразобранный JSON, ошибка API — всё это состояния `rerank_failed` с причиной и без фрагментов.
Доставить сырые кандидаты в этом случае значило бы вернуть ровно тот шум, который мы убираем,
и при этом выглядеть так, будто отбор состоялся.

**Порог и режим — настройки сессии, а не константы.** `enhanced` по умолчанию (ради него и делается
фаза), `baseline` — как было в P4, `/docs mode off` — без корпуса вовсе. Три уровня дают
пользователю честный выбор между качеством, расходом и отсутствием сети.

## Risks / Trade-offs

- [Лишний запрос на каждый вопрос с кандидатами] → это цена качества; `baseline` возвращает прежний
  расход, а при пустом корпусе оценки не запрашиваются вовсе.
- [Оценщик ошибается и отсеивает нужный фрагмент] → ассет требует оценивать всех и объяснять
  причину; при слабом отборе ответ всё равно формируется, а состояние видно в отчёте. Порог
  настраивается.
- [«Найдено, но не подошло» может скрыть полезный фрагмент] → пользователь видит журнальную строку
  и может посмотреть оценки в `/docs trace`, а `/docs retrieval baseline` возвращает прежнее
  поведение без отбора.
- [Разные модели по-разному понимают шкалу] → шкала описана в ассете с примерами по диапазонам;
  сравнение режимов на контрольных вопросах фиксирует фактический результат.
