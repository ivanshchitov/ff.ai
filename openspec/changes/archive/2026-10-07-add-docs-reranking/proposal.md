# Предложение: реранкинг кандидатов документации перед доставкой

## Why

Контрольный прогон P4 показал главную слабость корпуса: из трёх доставленных фрагментов релевантен
был один (вопрос про координаты — руководство по эмуляции плюс графика и типичные ошибки; вопрос
про `moc` — архитектура Qt плюс cmake и QCA). Поиск портала отдаёт всё, что хоть как-то совпало по
словам, а приложение передавало это модели целиком: лишние токены в каждом запросе и шум, который
модель вынуждена отбрасывать сама. Вопрос о версии при этом не попал в раздел примечаний к выпуску —
раздел был запрошен, но его попадания проиграли разделу документации, потому что отбор делает
портал своими словами, а не по смыслу вопроса.

Вторая ступень отбора — оценка кандидатов той же моделью сессии по порогу — решает обе задачи: до
модели доходят только релевантные фрагменты, а «нашлось, но не то» становится отдельным состоянием
с честной инструкцией вместо шума.

## What Changes

- **Оценка кандидатов моделью сессии.** После поиска приложение одним вспомогательным запросом
  просит оценить каждый кандидат по шкале 0..1 относительно исходного вопроса (не относительно
  переписанного запроса: переписывания здесь нет) с коротким объяснением. Запрос идёт с
  `max_tokens` из настроек, без температуры, в том же учёте расхода и с той же фазой спиннера, что
  другие вспомогательные запросы.
- **Порог и режимы.** Доставляются только кандидаты с оценкой не ниже порога (по умолчанию 0.6);
  число фрагментов остаётся ограниченным. Режим `enhanced` (по умолчанию) оценивает кандидатов,
  `baseline` работает как в P4 — без оценки. Переключается командой `/docs retrieval`.
- **Новое состояние `no_matches`.** Кандидаты есть, но ни один не прошёл порог: фрагменты не
  доставляются, а в запрос уходит инструкция не утверждать платформенные факты без источника;
  пользователь видит журнальную строку. Жёсткого отказа «отвечаю только по найденному» по-прежнему
  нет — это решение P4 (смежные вопросы уровня 3 должны отвечаться).
- **Отказ оценки — тоже состояние.** Неполный, дублирующийся, неизвестный или вне диапазона ответ
  оценщика, неразобранный JSON и ошибка API останавливают доставку с видимой причиной
  (`rerank_failed`): отвечать по сырым кандидатам нельзя — это ровно тот шум, который убираем.
- **Оценки и причины попадают в снимок.** Отчёт `/docs trace` показывает оценку и причину по каждому
  кандидату, а также какой порог и режим применялись: качество отбора должно быть проверяемым, а не
  заявленным.
- **Контрольный прогон сравнивает режимы.** Те же вопросы прогоняются в `baseline` и `enhanced`,
  результаты сравниваются по числу доставленных фрагментов и их релевантности.

## Capabilities

### New Capabilities

- `docs-reranking`: вторая ступень отбора кандидатов документации — оценка моделью сессии, порог,
  причины, состояния `no_matches` и `rerank_failed`, наблюдаемость отбора.

### Modified Capabilities

- `docs-retrieval`: доставка фрагментов теперь зависит от режима и порога; к прежним состояниям
  поиска добавляются `no_matches` и `rerank_failed`, а снимок получает оценки кандидатов.

## Критерии приёмки

- В `enhanced` до модели доходят только кандидаты с оценкой не ниже порога; лишние не попадают
  ни в запрос, ни в строку источников.
- «Нашлось, но не то» даёт состояние `no_matches`: фрагментов нет, инструкция есть, журнальная
  строка есть, ответ при этом возможен.
- Негодный ответ оценщика даёт `rerank_failed` с причиной и без фрагментов.
- `/docs retrieval baseline` возвращает поведение P4 (оценки нет, доставляются все кандидаты).
- Отчёт показывает оценки и причины, режим и порог.
- Живое сравнение режимов на контрольных вопросах: в `enhanced` доставленных фрагментов меньше,
  а доля релевантных выше.
