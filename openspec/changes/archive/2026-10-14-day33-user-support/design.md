## Context

См. `proposal.md`. День 33 ещё не сдан. Неделя 7 связывает RAG, инструменты и
автоматизацию; для этого дня достаточно цепочки «вопрос + тикет → MCP → RAG → модель → ответ».
Субагенты не входят в критерии и не нужны для короткого последовательного запроса.
Дни 31–32 реализованы; активных изменений нет, исходная ветка — main.

`AssistantSession._help_command` уже возвращает `CommandResult.answer`, источники,
события и метрики обоим интерфейсам. Локальный корпус и baseline-поиск существуют.
`mcp_registry` собирает серверы из домена и собственного сервера; CLI выбирает домен
через `--domain`. Предметные названия и правила запрещено переносить в core/ui.

## Goals / Non-Goals

**Goals:** один новый сценарий в существующем фасаде; отдельный домен `product-support`;
явное чтение выбранного обращения через MCP; воспроизводимый пример WebDavClient.

**Non-Goals:** настоящая CRM, вход пользователей и многопользовательская авторизация,
создание или изменение тикетов, автоматические исправления приложения, новое web-приложение,
изменение SDK и платформенные утверждения по памяти. Сервис запускается локально оператором
поддержки на доверенном наборе данных. Выбор тикета не является проверкой личности клиента.

## Decisions

### 1. Команда и домен

Добавить `/support <ticket-id> <вопрос>` в `AssistantSession.run_command` и каталог команд
TUI/web. Вызов обходит классификатор разработки. Домен `product-support` содержит
нейтральную роль поддержки, правила ответа, корпус Markdown, пустые настройки
платформенного поиска и узкие списки инструментов. Имя продукта и инструкции
по авторизации находятся в FAQ примера, не в ядре.

Альтернатива — обычный чат с автоматическим выбором инструментов — делает наличие
контекста тикета недетерминированным. Явная команда позволяет проверять каждый этап.

### 2. Один специализированный MCP-сервер

Новый `mcp_server/support_server.py` работает по stdio и предоставляет
`support_get_ticket(ticket_id)` с read_only_hint=true и отдельный health-инструмент.
Небольшой модуль чтения проверяет схему JSON: schema=1, списки users и tickets,
у каждого уникальный id, у тикета user_id. Используются безопасные поля по белому списку,
из свободного текста скрываются распознаваемые секреты существующим механизмом.
Лимит входного JSON — 1 MiB, результата — 16 000 символов. Симлинки не читаются.

Пакет домена получает необязательный `support.json`: относительный путь источника,
имя инструмента и правила контекста. Загрузчик проверяет данные, фабрика реестра строит
запуск собственного сервера абсолютным путём через sys.executable, передавая разрешённый
путь JSON аргументом. Источник обязан находиться внутри выбранного корня проекта;
обход границ и симлинки компонентов проверяются до чтения. Новые переменные окружения
не требуются. Пакеты без support.json сохраняют прежнее поведение.

Альтернатива — `repo_read` всего JSON — доставляет лишних пользователей и не проверяет
связи записей. Внешняя CRM потребовала бы доступов и не нужна по условию дня.

### 3. RAG и изоляция ответов

Переиспользовать индекс и CodeRetriever для FAQ/docs с проверкой свежести, как у `/help`.
Для команды выбирать baseline без вспомогательных модельных запросов, временно выключать
портал и auto_tools; восстанавливать настройки в finally. Поиск включает вопрос и безопасные
диагностические поля тикета (код ошибки, провайдер); продуктовые слова не зашиваются в код.
Фрагменты поступают с путями и строками через существующий механизм источников.

Ответ поддержки выполнять в отдельном коротком контексте: роль домена + вопрос + FAQ/docs +
результат MCP; история, память и профиль оператора не добавляются. Переиспользовать клиент
и учёт расхода сессии, но не подменять или очищать её историю. Не переносить ответ поддержки
в контекст следующего тикета. Возвращать обычный Answer/CommandResult.answer обоим UI.
Ошибки MCP останавливают доставку модели; отсутствие RAG объявляется явно, без придуманных
инструкций продукта. Отчёт содержит только доставленные источники и безопасный MCP-контекст.

### 4. Пример и демонстрация

В `examples/support-webdavclient/` разместить README, FAQ, документацию и support.json
с исключительно вымышленными пользователями/тикетами. Известные продуктовые шаги
сверить с доступной документацией и кодом WebDavClient; сценарные статусы обозначить
как тестовые данные, не реальные события сервиса. Не описывать платформу без портала.

Для запуска использовать временную git-копию примера (приложению нужен git-корень),
новый домен и полностью отдельные FFAI-пути. Демо: индекс FAQ/docs; MCP-контекст первого
тикета; вопрос об авторизации; источники и ответ; тот же вопрос для другого тикета;
изменение тестовой записи и свежий повтор; неизвестный тикет; trace и usage.
Запросы модели должны быть настоящими; локальные заглушки используются только в тестах.
Перед записью doctor и сухой прогон; запись экрана 30–600 с, проверка ключевых кадров.
При недоступной записи назвать причину и предоставить ручной сценарий.

## Risks / Trade-offs

- Свободный текст может содержать секреты → белый список, существующее скрытие секретов,
  только вымышленные данные демо; оператор проверяет частные данные перед подключением.
- Недостоверный ответ модели → проверенные RAG-источники, явные ограничения и ручной
  контроль двух ответов; недоступный источник не считается успешным этапом.
- Отдельный контекст может потерять разговорные уточнения → каждый запрос явно содержит
  вопрос и тикет; в объём дня не входит длительный диалог по обращению.
- Ограничения сети или записи экрана → фиксировать фактическую причину, не объявлять
  живую проверку или видео готовыми по результатам тестовой заглушки.

## Migration Plan

Добавление совместимо: новый домен выбирается явно, старые пакеты не требуют новых файлов.
Состояние остаётся вне целевого проекта. Пример и документация поставляются вместе с кодом.
Откат — запуск прежнего домена/версии; миграции пользовательских данных нет.
Предлагаемый следующий релиз — v0.33 после фактического v0.32.
Git-ветка, commit, tag, push и публикация требуют отдельного явного разрешения;
текущий запрос их не разрешает. Работать после согласования в текущем дереве либо
в новой ветке, если пользователь разрешит её создание.
