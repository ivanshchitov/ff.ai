## Context

См. `proposal.md` — Why. Донор (`tabletop-ai-assistant-tui`) — работающая механика агента, но
с тремя свойствами, мешающими переносу «как есть»: оркестрация живёт внутри терминального класса
(`ui/tui_app.py`, ~2 100 строк: он владеет агентом, настройками, моделью, прогоном задачи и рисует
экран), файлы состояния вычисляются от корня самого приложения (`core/config.py`, `BASE_DIR`), а
переменные окружения носят префикс `TABLETOP_*`. Домен (настольные игры) вшит в промпты, таблицу
инвариантов, таблицу маршрутизации памяти и корпус правил.

## Goals / Non-Goals

**Goals:**

- Один фасад сессии, пригодный для двух фронтендов (TUI сейчас, тонкий web в P9), без переписывания
  ядра на async.
- Адресация произвольного целевого репозитория и разделение «состояние пользователя» / «производные
  данные репозитория».
- Перенос слоёв донора без изменения их поведения и без регрессий: копирование с переименованием,
  а не переписывание.
- Домен разработки: системный промпт, отказ на внегематические вопросы, формат диффов.

**Non-Goals:**

- RAG по коду, MCP-инструменты, задача с валидацией тестами, память/профиль/инварианты, планировщик,
  локальная модель — следующие фазы (`docs/roadmap.md`). В P0 переносятся только слои без домена.
- Изменение репозитория-донора: он остаётся как есть.
- Асинхронное ядро, многопользовательский режим, сетевой доступ к сессии.
- Собственные спецификации перенесённых слоёв: их поведение не меняется, тексты импортируются
  отдельным изменением после P0.

## Decisions

**Фасад синхронный, с мьютексом и потоком событий.** Операции агента блокирующие (один HTTP-запрос
на вопрос), интерфейсов два, и оба хотят видеть прогресс. `AssistantSession` держит мьютекс
«одна операция за раз» и список подписчиков. Альтернативы: (а) async-ядро — пришлось бы переписать
весь `ui/` и прогон задачи ради того же поведения; (б) оставить оркестрацию в TUI и вынести её
позже — тогда при появлении web её пришлось бы переписывать второй раз. Мьютекс, а не очередь
задач: параллельные операции не нужны, а очередь создала бы невидимое пользователю отставание.

**События — типизированные, а не строки журнала.** `PhaseChanged`, `JournalLine`, `AnswerReady`,
`TaskStateChanged`. Свободный текст строки годится для печати в TUI, но web-слою нужно различать
фазу, строку и готовый ответ, иначе он начнёт парсить текст. Ошибка в подписчике не прерывает
операцию: интерфейс — наблюдатель, а не участник.

**Состояние: XDG для пользовательского, кэш по хешу пути для индекса.** Индекс — производное
от содержимого репозитория; держать его внутри целевого репозитория удобно, но это засоряет чужой
репозиторий и требует правки его `.gitignore`, то есть изменения файлов вне запрошенного изменения
(инвариант «не трогать лишнее»). Поэтому индекс лежит в
`/path/to/cache/ff-ai/path-hash/index.sqlite3`, где `path-hash` — хеш (sha1 от `realpath`) пути
целевого репозитория, а история, память, профиль, задачи, расписание и выгрузки —
в `/path/to/data/ff-ai/`. Каждая подсистема
переопределяется переменной `FFAI_*` — это же и есть механизм изоляции тестов, унаследованный
от донора.

**Копирование модулей донора вместо переписывания.** Слои без домена (API-клиент, настройки
ответа, стратегии контекста, сжатие, история, учёт расхода, панели-редьюсеры, чтение клавиш)
переносятся вместе с их unit-тестами; правки — только переименование и раскладка путей. Это
сохраняет накопленные решения (стриминг, сжатие, ветки, лимиты) и их регрессионную защиту.
Отдельно: `core/rules_index.py`, `core/rules_embeddings.py`, `core/rules_retrieval.py`,
`core/rules_citations.py`, `mcp_server/*` в P0 **не** переносятся — они приходят своими фазами
(P1–P4) и переписываются под новую предметную область.

**Корень проверяется на старте.** Целевой каталог обязан быть git-репозиторием; иначе приложение
завершается с ошибкой, называя путь и причину. Альтернатива — падать при первом вызове
инструмента: диагностика хуже, а половина возможностей молча не работает.

**Домен задаётся ассетами, а не кодом.** Роль, предметный отбор и текст отказа живут
в `assets/system_prompt.md` и `assets/answer_format_patch.md`; клиент вопросы не фильтрует —
решение донора, которое сохраняется (иначе появится второй, расходящийся с промптом, классификатор).

## Risks / Trade-offs

- [Копирование тянет балласт донора] → в P0 переносится только список слоёв из решения выше;
  остальное приходит своими фазами и переписывается.
- [Два фронтенда в одном процессе появятся только в P9] → фасад уже в P0 не зависит от `rich`
  и терминала; тест проверяет, что `core/` не импортирует `rich` и не читает stdin.
- [XDG-раскладка усложняет отладку («где мои файлы?»)] → команды-отчёты печатают фактические пути,
  а все переменные можно переопределить.
- [Мьютекс сериализует операции] → соответствует контракту агента (одна блокирующая операция);
  если в P9 понадобится параллельность, добавляется пул потоков на уровне web-слоя, ядро не меняется.
- [Перенос тестов тянет фикстуры донора] → `tests/e2e/harness.AppSession` переносится один раз,
  и правило донора сохраняется: новый файл состояния = новая переменная `FFAI_*` **и** проброс
  в harness, иначе тест пишет в реальные файлы пользователя.
- [Формат `patch` может конфликтовать с обязательными цитатами RAG (P2)] → `patch` — формат для
  показа изменения, он попадает под тот же STRICT-контракт, что JSON и compact; решение
  зафиксировано в спеке `question-answering` заранее, чтобы не менять её в P2.

## Migration Plan

Публичного API нет, донор не меняется, откат — удаление каталога. Порядок внутри фазы:
конфигурация и раскладка состояния → фасад и события → перенос слоёв → домен и ассеты → TUI →
тесты (unit → e2e в псевдотерминале) → документация (`README.md`, `CLAUDE.md`).

## Open Questions

- Точный набор типов событий уточнится в P9, когда появится web-подписчик; текущий набор
  покрывает фазы, строки журнала, готовый ответ и состояние задачи, и расширяется добавлением
  типа, не изменяя спек.
- Схема хеша пути репозитория (`sha1` от `realpath`) достаточна для разделения кэшей; смена схемы
  не влияет на поведение, кроме расположения индекса.
