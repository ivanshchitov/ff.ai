# Предложение: каркас ff.ai, фасад сессии и предметная область разработки

## Why

Консольный ассистент по настольным играм (`tabletop-ai-assistant-tui`) накопил всю механику
агента — контекст, память, профиль, MCP, RAG, состояние задачи, локальную модель, — но привязан
к предметной области и к самому себе: он отвечает про правила игр и умеет работать только
в собственном каталоге. Нужен ассистент по разработке: вопрос о кодовой базе с проверяемыми
ссылками `file:line` и задача по изменению кода с проверкой прогоном тестов. Механика при этом
переносится, а не пишется заново, поэтому первый шаг — фундамент: фасад сессии (чтобы интерфейсов
могло быть два), адресация целевого репозитория и предметная область.

## What Changes

- **Репозиторий `ff.ai`**: точка входа `ff-ai.py` (перезапуск в `.venv`), пакеты `core/` и `ui/`,
  `assets/`, `tests/`, `mcp_server/` (пустой до P3), OpenSpec-конфигурация.
- **Фасад сессии**: `core/session.py` — `AssistantSession` владеет агентом, настройками, моделью,
  состояние задачи и расписанием; операции `ask`, `run_command`, `task_step`, `report`;
  подписка на события (`PhaseChanged`, `JournalLine`, `AnswerReady`, `TaskStateChanged`);
  мьютекс «одна операция за раз». TUI и будущий web-фронтенд работают только через фасад.
- **Целевой репозиторий**: `--repo <путь>` → `FFAI_REPO_ROOT` → текущий каталог; корень обязан
  быть git-репозиторием, иначе явная ошибка старта; инструменты записи ограничены корнем.
- **Раскладка состояния**: история, память, профиль, задачи и расписание — в `/path/to/data/ff-ai`;
  индекс кода — в `/path/to/cache/ff-ai/path-hash/`; каждая подсистема переопределяется
  переменной `FFAI_*`.
- **Перенос слоёв без домена**: API-клиент, настройки ответа, стратегии контекста и сжатие,
  история диалога, учёт токенов и стоимости, панели-редьюсеры, чтение клавиш — как в доноре.
- **Предметная область как данные**: пакет `domains/aurora-qt5/` — область применимости
  (уровни «целевой репозиторий / платформа / смежное / вне области»), системный промпт роли,
  фиксированный текст отказа, таблица инвариантов платформы, правила памяти, разделы профиля,
  белые списки команд, состав корпусов и детерминированные проверки; загрузчик `core/domains.py`
  с проверкой схемы, автоопределением по маркерам репозитория и снимком домена.
- **Источник знаний о платформе**: домен объявляет MCP-сервер документации портала
  (`dev-aurora`, remote-транспорт, без токена) и версию документации; правка пакета меняет
  поведение без правки кода.
- **Форматы ответа**: `free`, `compact`, `json` из донора и новый `patch` для диффов.
- **Команды P0**: `/commands`, `/domain`, `/settings`, `/models`, `/context`, `/usage`, `/clear`,
  `/exit` с автодополнением по Tab; статус-бар с моделью, стратегией и расходом сессии.
- **BREAKING (относительно донора)**: интерфейс больше не владеет агентом — оркестрация переехала
  в фасад; префикс переменных окружения `TABLETOP_*` заменён на `FFAI_*`; состояние пользователя
  больше не лежит в корне проекта.

## Capabilities

### New Capabilities

- `session-facade`: единая точка входа для фронтендов — операции сессии, поток событий, сериализация
  операций и снимки состояния.
- `repo-targeting`: выбор целевого репозитория, проверка корня, раскладка состояния пользователя
  и индекса, ограничение файловых операций корнем.
- `question-answering`: содержательный ответ ассистента в границах активного домена и отказ
  на вопросы вне области применения; распределение инструкций формата и объёма между сообщениями
  запроса.
- `configuration`: внешняя конфигурация приложения — переменные окружения, значения по умолчанию,
  `.env.example` и поведенческие константы.
- `domain-profiles`: область применимости как пакет данных — тематика, источники знаний,
  ограничения, инструменты и проверки домена; выбор домена, проверка схемы пакета и границы
  расширения области.

### Modified Capabilities

Нет. Поведение перенесённых слоёв (форматы ответа, экран настроек, выбор модели, стратегии
контекста, история, учёт расхода, тестовая инфраструктура) не меняется относительно донора,
поэтому собственных дельт у них нет: их спецификации переносятся в `openspec/specs/` отдельным
изменением-импортом сразу после P0, с проверкой, что текст совпадает с фактическим поведением.

## Impact

- Код: `ff-ai.py` (новый), `core/session.py` (новый), `core/domains.py` (новый), `core/config.py`
  (переписан под `FFAI_*` и раскладку XDG), перенесённые модули `core/` и `ui/`.
- Данные домена: `domains/aurora-qt5/` (промпты, инварианты, память, профиль, инструменты,
  корпуса, проверки, сценарии).
- Тесты: `tests/e2e/harness.AppSession` с переопределением всех `FFAI_*`-путей состояния,
  `tests/unit/test_session.py`, `tests/unit/test_domains.py` (новые), перенесённые unit-тесты слоёв.
- Документация: `README.md`, `docs/design.md`, `docs/domains.md`, `docs/domain-aurora-qt5.md`,
  `docs/roadmap.md`, `CLAUDE.md` (создаётся на этой фазе).
- Зависимости: `rich`, `requests`, `python-dotenv`, `mcp` (Python 3.10+); в P0 новых нет.
- Совместимость: донор не меняется; ff.ai — отдельный репозиторий, общих файлов состояния нет.

## Критерии приёмки

- Приложение запускается в корне произвольного git-репозитория и отвечает на вопрос по разработке;
  запуск не в git-репозитории завершается понятной ошибкой.
- Активный домен распознаётся по маркерам репозитория или задаётся явно; вопрос вне области
  применения получает фиксированный отказ из пакета; правка пакета `domains/aurora-qt5/` меняет
  поведение без правки кода, а в `core/` и `ui/` нет идентификаторов из пакета.
- Вопрос не по теме разработки получает фиксированный отказ с объяснением причины и без ответа
  по существу.
- `/settings`, `/models`, `/context`, `/usage`, `/clear` работают без обращений к модели там, где
  это отчёт, и применяют изменения к следующим запросам.
- Фасад покрыт тестами без терминала: операции, события и отчёты проверяются на инъекции
  зависимостей, а также через реальный цикл в псевдотерминале.
- e2e-прогон не создаёт и не читает реальные файлы состояния пользователя.
